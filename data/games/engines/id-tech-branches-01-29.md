# Использование id Tech и все дальнейшие ветки развития у других разработчиков

## Вопросы 1–29

Этот файл собирает первые 29 пунктов исследования в одну непрерывную ветку: от первых попыток id Software лицензировать собственную технологию до открытой Quake-экосистемы, DarkPlaces, Nexuiz/Xonotic и современных коммерческих проектов на потомках Quake.

---

## 1. Как id Software вообще пришла к лицензированию своих движков другим студиям?

Лицензирование у id появилось очень рано — фактически ещё до Wolfenstein 3D и DOOM. И важный момент: это изначально не была идея Кармака в духе «давайте построим middleware-компанию». Модель выросла естественно из самого ритма разработки id: технология для самой id устаревала раньше, чем переставала быть передовой для остальных.

Уже в 1991 году id пыталась продавать другим разработчикам технологию Commander Keen. Джон Ромеро устраивал так называемый id Summer Seminar, где показывал разработчикам устройство Keen-технологии и возможность делать на ней собственные игры. Одним из результатов стало лицензирование технологии Apogee, которая затем использовала её для Bio Menace.

Базовая модель появилась уже тогда:

```text
id создаёт технологию
        ↓
делает на ней собственную игру
        ↓
Кармак уже пишет следующую технологию
        ↓
предыдущая всё ещё очень сильна
        ↓
её можно отдать другой студии
```

Особенно хорошо эта модель проявилась в сотрудничестве с Raven Software. После основной работы над Wolfenstein 3D Кармак уже экспериментировал с более продвинутым промежуточным renderer'ом: texture-mapped полами и потолками, более сложной геометрией и освещением. Для id это была уже переходная технология на пути к DOOM. Для Raven — практически космический фундамент, который небольшая студия сама могла бы писать годами. Raven получила этот pre-Doom engine и сделала на нём ShadowCaster.

Это и стало прототипом всей будущей экономики id:

```text
              id
               │
         R&D Кармака
               │
       ┌───────┴────────┐
       │                │
новая технология   предыдущая версия
для следующей игры    всё ещё сильнее
id                    большей части рынка
                          │
                     лицензирование
                          │
                    другая студия
```

DOOM уже доказал, что идея масштабируется. Raven получила Doom technology и сделала Heretic, а потом Hexen, всё сильнее меняя технологию под себя. Здесь id увидела очень важное свойство лицензирования: один renderer способен породить игры, которые сама id никогда бы не сделала.

Heretic превратил sci-fi/horror фундамент Doom в dark fantasy FPS, добавил inventory, полёт и собственные игровые системы. Hexen пошёл дальше: классы, hub structure, scripting, более сложное состояние мира. Движок переставал быть «кодом Doom» и становился технологической платформой.

Но настоящий engine licensing business начинается с Quake.

Причина проста: в 1996 году написать аналог Quake самостоятельно чрезвычайно дорого. Покупатель сразу получал:

- настоящий polygonal 3D;
- BSP;
- PVS;
- lightmaps;
- networking;
- collision;
- renderer;
- QuakeC;
- инструментарий;
- исходный код.

То есть он покупал не «графику Quake», а огромное количество уже решённых инженерных задач.

При этом ранняя id была довольно странной middleware-компанией. Технология — великолепная. Организация поддержки — далеко не уровня будущей Epic. В некоторых случаях модель почти сводилась к: вот вам исходники одного из лучших движков мира, дальше предполагается, что ваши программисты умеют читать C и разбираться сами.

К Quake III лицензирование стало заметно формальнее: существовали отдельные программы лицензирования Quake, Quake II и Quake III technologies, цены, договоры и technical support.

Особенно важно, что лицензирование идеально соответствовало психологии Кармака. Его цикл примерно такой:

```text
решить новую техническую проблему
        ↓
построить renderer
        ↓
выпустить игру
        ↓
эта проблема уже неинтересна
        ↓
идти к следующей
```

Поэтому для id старый движок быстро становился прошлым. Но рынок отставал. Когда id уже строила следующее поколение, прежнее всё ещё выглядело фантастически для другой студии.

Получалась почти идеальная экономика:

> id могла продавать то, что ей самой уже становилось неинтересно.

Позже появился второй слой — публикация исходников. Здесь важно не смешивать две модели:

```text
commercial proprietary licensing
```

Студия платит id, получает исходный код и право сделать закрытую коммерческую игру.

И:

```text
GPL source release
```

Старое поколение кода открывается для всего сообщества, но производные части движка должны соблюдать GPL.

В итоге id сначала создала рынок лицензирования движков, а затем ещё и создала условия для появления независимых open-source семейств этих же технологий.

### Главное

id пришла к лицензированию потому, что у неё возникла редкая технологическая машина:

**Кармак создавал движки быстрее, чем индустрия успевала их переваривать.**

Предыдущая технология одновременно могла быть:

- уже устаревающей для следующей игры id;
- передовой для другой студии;
- источником дополнительной выручки;
- способом распространить архитектуру id по всей индустрии.

Raven первой показала, что чужая студия может взять технологию id и сделать из неё другую игру.

Quake превратил эту идею из побочного заработка в настоящий технологический бизнес.

## 2. Насколько важным бизнесом для id было лицензирование технологий в 1990-х и 2000-х?

Лицензирование было важным, прибыльным и очень влиятельным направлением — но не главным бизнесом id Software.

Со стороны легко представить id как «Epic Games до Epic Games»: Quake, Quake II и Quake III действительно разошлись по большому количеству студий. Но сама id так никогда и не перестроилась в полноценную middleware-компанию.

В 1990-х схема была почти идеальной:

```text
1. собственная игра → продажи
2. собственная технология → можно продать ещё раз
```

Движок уже был оплачен разработкой Doom или Quake. Каждая лицензия превращала существующую R&D-работу Кармака в дополнительный доход.

В конце 1990-х лицензия Quake могла стоить порядка сотен тысяч долларов, а модель сделки могла включать upfront-платёж и процент от продаж. Для небольшой по численности id это были серьёзные деньги.

Но id не строила вокруг этого всю организацию.

Внутри компании обсуждалась идея более полноценного licensing-подразделения: отдельные продажи, отдельные специалисты поддержки, постоянная работа с лицензиатами. Однако Кармак гораздо сильнее интересовался созданием следующей технологии, чем обслуживанием десятков внешних компаний.

Вот фундаментальное различие:

```text
Epic постепенно строит:

движок
+ документация
+ support
+ developer relations
+ tooling
+ sales
+ middleware business
```

А id долгое время строит примерно:

```text
очень сильный движок
+ исходники
+ лицензия
+ ограниченная поддержка
```

К Quake II/Quake III направление уже стало формализованным. В 2000 году id официально предлагала Quake, Quake II и Quake III technologies. Например, после снижения цены Quake II engine предлагался за $125 000 flat fee. Для актуального Quake III применялись более дорогие схемы с upfront-платежами и royalties.

Есть особенно полезная цифра: Todd Hollenshead в начале 2000-х говорил, что engine licensing давал примерно **20% выручки id Software**.

Это идеальный масштаб:

```text
не мелкая побочка
```

но и:

```text
не основной бизнес
```

При этом влияние лицензирования на индустрию было намного больше, чем доход самой id.

Kevin Cloud позже говорил, что если сложить продажи игр, использовавших Quake, Quake II и Quake III technologies, получится свыше миллиарда долларов индустриальной выручки. Это, конечно, не миллиард id. Это деньги всех игр, выросших на её технологиях.

И здесь особенно показателен Call of Duty:

```text
id Tech 3
   ↓
Medal of Honor lineage
   ↓
Infinity Ward
   ↓
Call of Duty
   ↓
IW Engine
```

id получает лицензионные деньги один раз. А технологическое семя продолжает жить десятилетиями в одной из крупнейших игровых франшиз мира.

Почему id в итоге не стала Epic?

Потому что у них были разные продуктовые приоритеты.

Epic всё сильнее решала задачу:

> как сделать движок удобным продуктом для других разработчиков?

Кармак в первую очередь решал:

> как сделать следующий технический скачок?

Это две разные организации.

Во времена Quake III технология id находилась в центре рынка. Но затем Unreal Engine всё сильнее закреплялся как универсальный middleware. id Tech 4 получила уже заметно меньше внешних лицензиатов.

К id Tech 5 id попыталась вернуться к более серьёзной борьбе за рынок: улучшить tools, поддержку, multiplatform pipeline, сделать технологию удобнее для внешних команд. Сотрудники id прямо признавали, что Unreal фактически занял большую часть high-end engine licensing рынка.

Но в 2009 году ZeniMax покупает id Software, и экономическая логика меняется.

Раньше:

```text
больше внешних лицензиатов
→ больше денег id
```

После покупки:

```text
id Tech
→ конкурентное преимущество группы ZeniMax
```

Технология начинает распространяться прежде всего внутри группы:

- MachineGames;
- Arkane;
- Tango;
- другие внутренние команды.

То есть id Tech постепенно перестаёт быть товаром и становится внутренним стратегическим активом.

### Четыре эпохи

```text
1991–1995
ЭКСПЕРИМЕНТ
Keen / Doom
```

```text
1996–2001
РАСЦВЕТ
Quake / Quake II / Quake III
```

```text
2002–2008
УТРАТА ЛИДЕРСТВА
id Tech 4 → id Tech 5
Unreal всё сильнее доминирует
```

```text
2009+
ВНУТРЕННЯЯ ТЕХНОЛОГИЯ
ZeniMax
```

Итог: лицензирование было стратегически значимым бизнесом и в лучшие годы давало заметную долю выручки, но id никогда не перестраивала всю компанию вокруг него.

Она помогла создать сам рынок коммерческого engine licensing.

А империю на этом рынке в итоге построила Epic.

## 3. Что получал разработчик при покупке лицензии id: исходный код, инструменты, поддержку, редакторы?

Не существовало одного неизменного «пакета id Tech». Состав менялся от Quake к Quake III и Doom 3. Но ядро сделки было достаточно стабильным:

**исходный код движка + право модификации и коммерческого выпуска + production tools + документация + ограниченная поддержка.**

Главное — именно исходники.

Лицензиат не получал закрытый:

```text
Engine.dll
↓
вот API
↓
внутрь не лезть
```

Он мог менять:

- renderer;
- networking;
- filesystem;
- collision;
- client/server;
- game layer;
- platform code;
- asset pipeline.

Именно поэтому чужие проекты могли уходить настолько далеко.

Valve начала с Quake и постепенно получила GoldSrc.

Infinity Ward начала с id Tech 3 lineage и пришла к IW Engine.

Raven десятилетиями выращивала свои ветки.

Human Head могла радикально менять id Tech 4 под Prey.

Важно: engine source не означал, что покупателю отдавали Quake/Doom вместе со всеми игровыми ресурсами. Assets — текстуры, уровни, модели, музыка, звуки — оставались отдельной интеллектуальной собственностью. Покупалась технология для создания **своей** игры.

К Quake III production pipeline уже был весьма зрелым. Вокруг движка существовали:

- Q3Radiant;
- q3map;
- BSP tools;
- bot navigation compilers;
- C/QVM toolchain;
- renderer;
- game code;
- platform/runtime code.

Схема уровня:

```text
Radiant
   ↓
.map
   ↓
q3map
   ↓
.bsp
   ↓
engine
```

То есть покупатель получал не только renderer, но и основу production pipeline.

С id Tech 4 подход стал ещё интереснее. Doom 3 имел встроенные в executable редакторы:

- DoomEdit;
- GUI editor;
- material editor;
- particle editor;
- script/debug tools;
- Maya/export tooling.

Система уже выглядела как полноценная среда разработки:

```text
Maya / DCC
    ↓
export tools
    ↓
models / animations
    ↓
DoomEdit / material / GUI tools
    ↓
engine
```

Но по сравнению с современным Unreal документация и support были намного более инженерными.

Предполагалось, что команда умеет:

- читать C/C++;
- разбираться в большой чужой codebase;
- самостоятельно адаптировать движок;
- самостоятельно писать недостающие системы.

Ранняя поддержка id иногда была почти анекдотически маленькой. Кармак вспоминал модели договора, где в лицензии могло фигурировать буквально несколько часов технической поддержки: приехали, поговорили с инженерами id, дальше разбирайтесь.

К Quake III поддержка стала формальнее, но культурно id всё равно оставалась ближе к:

> технологической лаборатории, которая иногда продаёт свой код,

чем к:

> middleware-компании, построенной вокруг поддержки внешних разработчиков.

Также надо различать три режима доступа.

### Commercial engine license

```text
исходники
+
право сделать standalone proprietary game
```

### Mod SDK

```text
часть game source / tools
+
делай мод для существующей игры
```

### GPL source

```text
полный открытый старый engine
+
можно делать самостоятельный продукт,
но derivative engine code должен соблюдать GPL
```

Эти модели юридически совершенно разные.

### Что получал покупатель по сути

1. Engine source code.
2. Право коммерческого использования по договору.
3. Renderer.
4. Networking.
5. Collision/physics infrastructure.
6. Client/server framework.
7. Filesystem и asset loading.
8. Game-code framework.
9. Level tools.
10. Map compiler.
11. Asset conversion/export pipeline.
12. Sample/game code.
13. Documentation.
14. Обновления и исправления в рамках договора.
15. Некоторую техническую поддержку.

И дальше начиналась работа самой студии.

Именно поэтому лицензирование id исторически порождало не только «игры на Quake», но и **новые движковые семейства**.

## 4. Почему технологии id так часто становились основой чужих движков, а не просто использовались без изменений?

Потому что id продавала не закрытый продукт с жёсткой рамкой API, а исходный код очень сильного технологического фундамента.

Лицензиат почти неизбежно приходил к мысли:

> лучше изменить движок под нашу игру, чем изменить игру под ограничения движка.

Доступ к source позволял менять буквально всё:

```text
renderer
networking
filesystem
collision
animation
tooling
asset formats
game loop
```

Именно архитектура сделки провоцировала форки:

```text
купили engine source
        ↓
добавили нужные системы
        ↓
переписали неудобные части
        ↓
ещё раз переписали
        ↓
через несколько лет это уже
практически собственный движок
```

Вторая причина — id делала движки под **свои конкретные игры**.

Quake III проектировался вокруг:

- multiplayer;
- арен;
- малого числа игроков;
- высокой скорости;
- ограниченной сюжетной логики.

А лицензиаты хотели:

- Medal of Honor;
- Call of Duty;
- Jedi Knight;
- Return to Castle Wolfenstein.

Например Call of Duty требовал:

```text
массовые scripted battles
десятки AI-солдат
cinematic sequences
новую animation system
новое lighting
```

Поэтому Infinity Ward пришлось расширять и менять технологию. Уже в первом Call of Duty появились собственные renderer/animation/light compilation решения.

Третья причина — фундамент id был действительно силён.

Самые дорогие инженерные задачи уже решены:

```text
rendering
networking
filesystem
entity framework
collision
BSP
visibility
client/server
platform abstraction
toolchain
```

Поэтому студии не начинали с пустого файла.

Они начинали с работающего AAA-фундамента и тратили время на то, что делало их игру другой.

Но свобода могла быть опасной. Daikatana — классический контрпример: попытка перейти с Quake на Quake II codebase привела к огромной технической задержке. Возможность менять всё не гарантирует, что команда умеет управлять такой миграцией.

Четвёртая причина — id не требовала поддерживать идеальную совместимость с upstream.

Можно было:

```text
fork
↓
переписать renderer
↓
поменять asset formats
↓
добавить AI
↓
переписать tools
↓
никогда больше не merge'ить upstream
```

Отсюда возникает fork divergence.

И через несколько лет:

```text
«лицензированный id engine»
```

становится:

```text
«наш engine,
который когда-то начался с id Tech»
```

Так родились важнейшие линии:

```text
Quake
  ↓
GoldSrc
  ↓
Source
  ↓
Source 2
```

```text
id Tech 3
  ↓
Call of Duty technology
  ↓
IW Engine
```

```text
id Tech 5
  ↓
Arkane modifications
  ↓
Void
```

```text
id Tech 5
  ↓
Tango modifications
  ↓
Stem
```

```text
id Tech 7
  ↓
MachineGames
  ↓
Motor
```

Это и есть главная причина: исходники были не бонусом лицензии. Исходники были самой сутью лицензирования id.

## 5. Какие сторонние игры первыми получили Doom engine?

Первой по-настоящему важной внешней игрой на Doom engine стала **Heretic** от Raven Software в 1994 году.

ShadowCaster был раньше, но использовал промежуточную pre-Doom технологию Кармака, поэтому полноценная внешняя ветка именно Doom engine начинается с Heretic.

Ранняя схема:

```text
DOOM — 1993
id Software
   │
   └── Raven получает Doom technology
          │
          ▼
Heretic — 1994
          │
          ▼
Hexen — 1995

отдельная Doom-derived ветка
          │
          ▼
Strife — 1996
```

Heretic был важен не как «Doom с фэнтези-текстурами». Raven добавила:

- inventory;
- usable artifacts;
- flight;
- look up/down;
- более осмысленную вертикальную collision;
- новые projectile systems;
- дополнительные environmental effects.

То есть уже первая крупная лицензия Doom дала самостоятельный technological fork.

В 1995 году Raven выпускает Hexen и идёт намного дальше:

- классы;
- hubs;
- persistent world state;
- ACS scripting;
- polyobjects;
- parameterized specials;
- сложную puzzle/world logic.

Генеалогия:

```text
Doom
  │
  └── Heretic
        │
        └── Hexen
```

Параллельно Rogue Entertainment делает **Strife** — уже совсем другую мутацию Doom: NPC, диалоги, квесты, магазины, выборы, RPG-прогрессию.

То есть к 1996 году существуют минимум две очень разные внешние философии:

```text
Doom
 ├── Raven → Heretic → Hexen
 │            scripting / hubs / fantasy
 │
 └── Rogue → Strife
              dialogue / RPG / narrative
```

Doom II сюда не относится — это сама id.

Final Doom технологически ближе к коммерческим content packs на Doom II engine, а не к самостоятельному engine fork.

Doom 64 уже интереснее: Midway серьёзно адаптировала Doom technology под Nintendo 64, и эту ветку можно считать отдельной консольной мутацией.

Chex Quest показывает ещё одну крайность: тот же технологический фундамент можно превратить из ультражестокого шутера в детскую рекламную игру.

### Главное

Heretic впервые убедительно доказал:

> Doom engine — это не только технология Doom.

Hexen показал:

> эту технологию можно развивать как самостоятельную платформу.

Strife доказал:

> из неё можно выжать даже FPS/RPG с NPC и диалогами.

И с этого момента Doom engine окончательно становится самостоятельным технологическим активом id.

## 6. Как Raven Software переделала Doom engine для Heretic?

Heretic не переписал Doom с нуля. Основа осталась узнаваемой:

- BSP;
- sectors;
- linedefs;
- WAD;
- sprites;
- Doom-подобная state/entity system.

Raven полезла прежде всего туда, где Doom ограничивал именно игровую систему.

### Look up/down

Doom фактически держит горизонт камеры неподвижным. Raven реализовала дешёвый, но эффективный вариант через сдвиг горизонта — разновидность y-shearing.

```text
обычный Doom:

---------------- horizon ----------------


Heretic, взгляд вверх:

        ---------------- horizon ----------------
```

Это не настоящий свободный pitch как в Quake: при больших углах появляются искажения, поэтому диапазон пришлось ограничивать.

Интересно, что Raven экспериментировала и с полноценным mouse-look, но команда тогда не считала это особенно нужным.

### Полёт

Wings of Wrath делают `z` координату полноценной частью управления:

```text
Doom:
x, y
z в основном задаётся полом/падением

Heretic:
x, y, z
игрок сознательно меняет высоту
```

Это сразу потребовало менять movement, gravity, collision, view height и взаимодействие с объектами.

### Z-clipping

Doom во многих местах мыслит actors почти как бесконечно высокие столбы. Для полёта это плохо.

Heretic начинает серьёзнее учитывать:

- `z` объекта;
- его высоту;
- вертикальное пересечение.

Благодаря этому можно проходить под летающими врагами и осмысленнее взаимодействовать с пространством по вертикали.

### Inventory

Doom:

```text
pickup
↓
эффект сразу применяется
```

Heretic:

```text
pickup
↓
inventory
↓
выбираем предмет
↓
используем когда нужно
```

Появляются Quartz Flask, Mystic Urn, Wings of Wrath, Ring of Invincibility, Tome of Power, Morph Ovum, Chaos Device, Time Bomb и другие предметы.

Это требует уже полноценного persistent state игрока.

### Tome of Power

Raven расширяет weapon state system так, что практически каждое оружие имеет усиленное поведение.

Это ещё не современный secondary fire по RMB, но уже идея:

```text
weapon
↓
power mode
↓
альтернативное поведение
```

### Morph Ovum

Превращение врагов и игрока в курицу выглядит шуткой, но технически затрагивает actor type, collision height, movement, view height, attack и обратное превращение.

Особенно интересен edge case:

```text
игрок-курица
↓
залез в низкую щель
↓
эффект закончился
↓
человек здесь не помещается
```

Нужно отдельно проверять возможность unmorph.

### Sector forces

Raven расширяет sector logic:

```text
sector
↓
current / wind
↓
actor momentum
```

Появляются течения и ветер. Environment начинает участвовать в механике, а не просто быть декорацией.

### Ambient audio

Heretic расширяет звуковую сцену:

- капли;
- цепи;
- далёкие шумы;
- атмосферные environmental sounds.

### Итоговая архитектура

```text
                    DOOM ENGINE
                         │
       ┌─────────────────┼──────────────────┐
       │                 │                  │
     renderer          physics          game logic
       │                 │                  │
 y-shearing         flight / z          inventory
 look up/down       clipping            artifacts
                                            │
                                            ├─ Tome
                                            ├─ Morph
                                            └─ usable items

                         │
                      sectors
                         │
                  currents / wind

                         │
                       audio
                         │
                  ambient sounds
```

Heretic важен тем, что Raven не стала переписывать сильный Doom-фундамент. Она вложилась туда, где дизайн её игры действительно требовал изменений.

И именно из этой ветки затем вырастет Hexen.

---

## 7. Что Hexen изменил в Doom engine по сравнению с Heretic?

Hexen — момент, когда Raven начинает превращать Doom engine уже в собственную authoring/runtime platform.

Heretic в основном расширял gameplay.

Hexen меняет:

- формат карт;
- логику уровня;
- scripting;
- persistent world;
- динамическую геометрию.

### ACS

Главный скачок — **Action Code Script**.

Doom/Heretic:

```text
игрок пересёк линию
↓
hardcoded special
↓
поднять floor / открыть door
```

Hexen:

```text
trigger
↓
script
↓
закрыть дверь
↓
выключить свет
↓
подождать
↓
поднять колонны
↓
spawn monsters
```

ACS компилируется в bytecode и хранится в `BEHAVIOR` lump. Runtime имеет отдельный interpreter.

То есть Raven фактически встроила в Doom маленькую scripting VM.

### Параметризованные specials

Вместо старой модели:

```text
special + sector tag
```

Hexen получает:

```text
special
+ arg0
+ arg1
+ arg2
+ arg3
+ arg4
```

Это уже ближе к API.

### TID

Things получают идентификаторы и дополнительные параметры. Скрипт может адресовать конкретные объекты в мире.

```text
world object
      ↑
 identifier
      ↑
 script
```

### Hub system

Doom:

```text
MAP01
 ↓
MAP02
 ↓
MAP03
```

Hexen:

```text
              MAP03
                ↑
                │
MAP04 ←──── HUB MAP02 ────→ MAP05
                │
                ↓
              MAP06
```

Игрок возвращается на старые карты, а они должны помнить:

- убитых врагов;
- поднятые предметы;
- открытые двери;
- активированные события.

Это уже world persistence.

### Polyobjects

Doom умеет двигать floor/ceiling, но XY-стены практически статичны.

Hexen добавляет polyobjects:

- sliding doors;
- swinging doors;
- вращающиеся стены;
- движущиеся препятствия.

Это не полностью динамическая геометрия Quake, но серьёзное расширение статического BSP-world.

### Jump

Hexen добавляет обычный прыжок и связанные с ним вертикальные механики.

### Классы

Появляются:

- Fighter;
- Cleric;
- Mage.

У них разные:

- weapons;
- health;
- armor;
- mana;
- combat roles.

### Level designers получают больше власти

Doom:

```text
движок умеет набор действий
дизайнер их комбинирует
```

Hexen:

```text
движок даёт primitives
дизайнер пишет последовательность действий сам
```

Именно поэтому можно строить большие puzzle chains и cross-map события.

Обратная сторона — знаменитая проблема «something opened somewhere»: инструменты стали сложнее, а UX для объяснения игроку причин и последствий ещё не вырос.

### Итог

```text
DOOM
│
├── hardcoded specials
├── static XY geometry
├── linear maps
└── simple map lifetime
     │
     ▼
HERETIC
│
├── inventory
├── flight
├── look up/down
├── better z interaction
└── richer gameplay
     │
     ▼
HEXEN
│
├── ACS scripting VM
├── parameterized specials
├── TIDs
├── expanded map format
├── hubs
├── persistent map state
├── polyobjects
├── jumping
├── player classes
└── scripted world behavior
```

Heretic расширил Doom как игру.

**Hexen расширил Doom как платформу для создания игры.**

---

## 8. Можно ли считать движок Hexen самостоятельной веткой Doom engine?

Да — если говорить о самостоятельной ветви внутри семейства Doom engine, а не о полностью новом движке с нуля.

Правильная генеалогия:

```text
Doom engine
   │
   └── Heretic branch
          │
          └── Hexen branch
```

Фундамент всё ещё Doom:

- BSP;
- sectors;
- linedefs;
- sidedefs;
- sprites;
- WAD;
- thinker/mobj ancestry;
- software renderer;
- Doom-like game loop.

Но поверх него появляется собственная инфраструктура Raven:

```text
ACS
BEHAVIOR bytecode
parameterized specials
TID
expanded map format
hub persistence
polyobjects
jumping
classes
complex scripted events
```

Это уже отдельный runtime dialect.

Особенно важен ACS: уровень превращается из набора геометрии и специальных линий в частично программируемый объект.

Polyobjects добавляют отдельный manager динамической геометрии.

Hub system требует иной модели сохранения состояния мира.

Поэтому степень родства можно представить так:

```text
Doom
  │
  ├── Doom II
  │     почти та же основная линия
  │
  └── Heretic
        заметный fork
          │
          └── Hexen
                самостоятельная развитая ветка
```

Но renderer и low-level world model всё ещё достаточно Doom-derived, чтобы не называть Hexen совершенно новым независимым engine family.

Самая точная формулировка:

> Hexen engine — сильно модифицированный descendant Doom engine, сформировавший отдельную Raven-ветку и собственный map/runtime dialect.

Именно поэтому решения Hexen пережили саму Hexen.

Позднее ZDoom/GZDoom наследует или переосмысляет:

- Hexen map format;
- ACS;
- parameterized specials;
- TID;
- polyobjects;
- hub-like concepts.

То есть Raven в 1995 году создала надстройку, которая стала одним из фундаментов современной Doom source-port экосистемы.

---

## 9. Как Strife использовала и расширяла технологию Doom?

Strife — одна из самых необычных мутаций Doom engine.

Rogue Entertainment попыталась сделать поверх него то, что позже назвали бы FPS/RPG с immersive-sim элементами.

База остаётся Doom-derived:

```text
BSP
sectors
linedefs
sprites
mobj/state system
WAD
software renderer
```

Но поверх неё появляются:

- NPC;
- диалоги;
- квесты;
- торговцы;
- валюта;
- сюжетное состояние;
- хабовый мир;
- выборы;
- несколько концовок;
- RPG-прогрессия.

### NPC

Doom мыслит сущностями примерно так:

```text
monster
pickup
projectile
decoration
player
```

Strife добавляет:

```text
NPC
```

Actor может:

```text
стоять в мире
↓
не атаковать
↓
начать разговор
↓
проверить состояние квеста
↓
выдать предмет
↓
изменить progression
```

### Диалоговая система

Диалоги хранятся как данные в специальных lumps.

У диалога есть:

- speaker;
- текст;
- voice;
- варианты ответа;
- требования к предметам;
- награды;
- переходы;
- последствия выбора.

То есть появляется data-driven narrative layer.

### Экономика

Предмет теперь может быть:

```text
combat pickup
quest item
currency
trade good
key item
```

Появляются торговцы и покупки.

### Quest state

Doom level logic в основном локальна:

```text
switch → door
```

Strife требует:

```text
что игрок уже сделал
↓
что знает NPC
↓
какую реплику показать
↓
какой маршрут открыть
↓
какой финал доступен
```

Это persistent narrative state.

### Хабы

Hexen использовал hub прежде всего как spatial/puzzle structure.

Strife:

```text
hub
↓
социально-сюжетный центр
```

Туда возвращаются ради NPC, торговцев, базы сопротивления, новых диалогов и заданий.

### Friendly / neutral / hostile

Мир должен различать отношения акторов к игроку. Это уже сложнее обычного Doom:

```text
monster sees player
↓
attack
```

### Stealth-like элементы

Strife экспериментирует с тихим устранением врагов и ситуациями, где не вся зона мгновенно переходит в боевое состояние.

Это не Thief, но направление принципиально другое.

### RPG-прогрессия

Игрок может повышать максимальное здоровье и точность.

```text
player state
↓
постоянно улучшается
```

### Несколько концовок

Финал зависит от сюжетного состояния и решений.

### Voice acting

Диалоговая система умеет связывать текст с voice resources.

Получается:

```text
NPC interaction
↓
portrait
↓
text
↓
voice
↓
choices
```

### Но геометрически это всё ещё Doom

Strife не превратил Doom в Quake.

Остаются:

- sectors;
- BSP;
- вертикальные стены;
- flat floors/ceilings;
- sprite actors;
- 2.5D world constraints.

То есть Rogue радикально меняет:

```text
game logic
AI
dialogue
quests
world state
inventory/economy
```

а не renderer.

### Hexen vs Strife

```text
                 Doom
                  │
        ┌─────────┴─────────┐
        │                   │
      Hexen               Strife
        │                   │
 scripting              dialogue
 polyobjects            quests
 hubs                   NPCs
 classes                shops
 puzzles                choices
 world scripting        narrative state
```

Hexen делает Doom более мощной level-design platform.

Strife делает Doom narrative/RPG platform.

Особенно интересна дальнейшая судьба Strife: оригинальный source code оказался утрачен, и позднее community пришлось восстанавливать поведение через reverse engineering бинарника и сопоставление с открытыми родственными Doom codebases. Поэтому Veteran Edition фактически выросла из реконструированной community-реализации.

Это натуральная программная археология.

## 10. Какие ещё коммерческие игры 1990-х строились непосредственно на Doom engine?

Если считать строго, список не бесконечен. Но вокруг Doom возникло несколько разных типов коммерческих потомков:

```text
1. полноценные лицензированные forks
2. официальные сторонние ветки
3. коммерческие total conversions
4. reverse-engineered родственники
```

### Chex Quest

Один из самых забавных примеров.

Digital Café в 1996 году получила право использовать Doom technology для рекламной игры General Mills.

```text
The Ultimate Doom
      │
      └── Digital Café
             ↓
         Chex Quest
```

Технологически это Doom-derived самостоятельный продукт с новыми уровнями, оружием, врагами, графикой и изменённым поведением.

Самое смешное: движок, известный мясом, демонами и сатанинской паникой, превращается в детскую игру из коробки хлопьев.

Chex Quest 2 продолжает ту же ветку, но ближе к addon/content continuation.

### Killing Time PC

Оригинальный Killing Time на 3DO использовал другую технологию, но PC/Mac-версия была переделана на engine, происходившем от Jaguar Doom.

Получается:

```text
Doom PC
   ↓
Jaguar Doom
   ↓
Killing Time PC
```

Это уже полноценное использование Doom-derived runtime для совершенно другой коммерческой игры.

### Doom 64

Midway серьёзно переделала Doom technology под Nintendo 64:

- аппаратно-ориентированный renderer;
- новую lighting/presentation модель;
- собственные assets;
- адаптированную map/runtime логику.

Это официальная консольная ветка:

```text
Doom technology
       ↓
id + Midway
       ↓
Doom 64
```

### Hacx

Hacx — коммерческий Doom II total conversion.

Но важно: его разработчики не получили engine source так, как Raven.

Схема:

```text
Doom II binary
+
DeHackEd
+
новые assets
+
новые maps
=
commercial TC
```

Поэтому технологически это не самостоятельная codebase-ветка уровня Heretic.

### Final Doom

Коммерчески важен, но технологически в основном:

```text
Doom II engine
+
чужой content
```

а не новый engine fork.

### Азиатская периферия

Существовали малоизвестные Doom-related продукты вроде:

- A.D. Cop;
- Mars 3D;
- 3D Hero;
- TAO.

Здесь происхождение сложнее. Часть технологий выглядит как reverse engineering Doom/Hexen, а Mars 3D связывают ещё и с идеями Build.

Поэтому их разумнее рисовать пунктирной линией:

```text
Doom / Hexen
     ──────→ A.D. Cop

Doom + Build
     ──────→ Mars 3D
                │
            ┌───┴───┐
         3D Hero   TAO
```

а не ставить рядом с официальной лицензией Raven.

### Итоговое дерево коммерческой эпохи Doom

```text
                         DOOM ENGINE
                              │
        ┌─────────────────────┼──────────────────────┐
        │                     │                      │
   licensed forks       official branches      commercial TCs
        │                     │                      │
     Heretic               Doom 64                 Hacx
        │
      Hexen

     Strife

   Chex Quest
        │
   Chex Quest 2

   Killing Time PC
   (через Jaguar Doom)
```

К 1997 году Doom уже технологически уступал Quake, но оказался настолько понятным, пластичным и доступным, что продолжал порождать новые продукты.

А затем в декабре 1997 года id публикует исходники Doom — и история полностью меняется.

---

## 11. Что произошло с Doom engine после открытия исходного кода?

23 декабря 1997 года id Software публикует исходный код Doom. И вот здесь заканчивается первая жизнь движка как технологии, которую id контролирует и лицензирует отдельным студиям, и начинается вторая жизнь — **community-driven эволюция**.

До этого:

```text
id / коммерческая лицензия
        │
        ├── Raven → Heretic → Hexen
        ├── Rogue → Strife
        └── другие коммерческие ветки
```

После публикации:

```text
                 DOOM SOURCE
                     │
      ┌──────────────┼───────────────┐
      │              │               │
   сохранить      улучшить        радикально
 оригинальный      Doom          расширить Doom
      │              │               │
 Chocolate       Boom/MBF        ZDoom/EDGE/
 Doom и т.п.     PrBoom          Legacy/и т.д.
```

Важно: id первоначально публикует не DOS-версию, а Linux Doom source. DOS-код содержал лицензированные сторонние компоненты, прежде всего вокруг звука, которые нельзя было просто открыть.

Поэтому первые энтузиасты фактически начинают **портировать Doom обратно** на Windows/DOS/другие системы. Отсюда закрепляется термин `source port`.

Кармак в README почти выдал сообществу roadmap:

- transparency;
- look up/down;
- slopes;
- jumping;
- ducking;
- flying;
- client/server networking;
- hardware-accelerated rendering;
- новые weapons.

Сообщество затем реализовало почти всё перечисленное и огромное количество вещей, которых в этом списке вообще не было.

### Сначала лицензия была не GPL

Первый release 1997 года использовал специальную Doom Source License. Она позволяла изучать и модифицировать код, но ограничивала коммерческое использование.

В 1999 году Кармак перелицензирует Doom под GNU GPL.

И вот это уже настоящий перелом:

```text
читать код                  ✓
модифицировать              ✓
распространять              ✓
коммерчески использовать    ✓
при соблюдении GPL          ✓
```

GPL превращает Doom из «открытого старого исходника» в полноценный открытый технологический фундамент.

### Возникает первое поколение source ports

К концу 1990-х появляются:

- DOSDoom;
- Boom;
- MBF;
- ZDoom;
- Doom Legacy;
- glDoom;
- Doomsday/jDoom;
- Eternity;
- другие проекты.

И Doom перестаёт иметь один canonical engine.

### Boom

TeamTNT пытается сделать не «совершенно новый Doom», а условный **Doom 2.0**:

```text
исправить баги
+
снять ограничения
+
дать mapper'ам новые возможности
+
сохранить ощущение Doom
```

Boom добавляет:

- scrolling floors/walls;
- conveyor belts;
- friction;
- translucency;
- silent teleporters;
- custom colormaps;
- generic linedef actions;
- расширенный DeHackEd/BEX;
- снятие множества vanilla limits.

И Boom compatibility сама становится стандартом контента.

### MBF

Lee Killough развивает Boom дальше:

```text
Doom
 ↓
Boom
 ↓
MBF
```

MBF добавляет собственные gameplay/AI/editing возможности и становится ещё одним compatibility target.

### ZDoom

ZDoom выбирает другую философию:

```text
не:
как сохранить Doom

а:
что вообще можно построить
поверх Doom architecture?
```

Он начинает собирать возможности разных веток:

- Doom;
- Heretic;
- Hexen;
- Strife;
- Boom;
- ACS;
- Hexen map format;
- freelook;
- jumping;
- современное управление;
- расширенную вертикальную физику.

### EDGE

DOSDoom/EDGE развивает идею data-driven gameplay через DDF и другие definition systems.

Вместо патчинга executable:

```text
DeHackEd
```

появляется возможность описывать:

- weapons;
- monsters;
- attacks;
- effects;

через внешние данные.

### Preservation

Одновременно возникает противоположная философия:

> не улучшать Doom, а максимально точно сохранить поведение DOS Doom.

Эту линию позже особенно хорошо воплотит Chocolate Doom.

Получается:

```text
                Doom source
                    │
          ┌─────────┴─────────┐
          │                   │
      PRESERVATION          EVOLUTION
          │                   │
   Chocolate Doom       ZDoom/GZDoom
```

Между ними существуют Boom/MBF/PrBoom-подобные компромиссные ветки.

### Doom становится платформонезависимым

После публикации source идея «порт Doom на новую платформу» перестаёт быть только проектом официального издателя.

Появляется:

```text
есть C source
↓
пишем platform layer
↓
DOOM работает где угодно
```

И отсюда вырастает мем:

**But can it run Doom?**

### Content modding + engine modding

До source release пользователь мог менять:

- WAD;
- maps;
- textures;
- sprites;
- звуки;
- часть таблиц через DeHackEd.

После release появляется новый уровень:

```text
ENGINE MODDING
```

Теперь если renderer не умеет X:

```text
открываем source
↓
пишем X
```

И дальше происходит важнейший community cycle:

```text
source port добавляет feature
↓
mapper использует её
↓
feature становится популярной
↓
другие ports добавляют compatibility
↓
рождается новый community standard
```

Именно так Boom-совместимость пережила сам Boom.

### Главное

После 1997 года разработку Doom engine фактически забирает сообщество.

id уходит:

```text
Doom
↓
Quake
↓
Quake II
↓
Quake III
```

Community идёт:

```text
Doom source
↓
Boom / ZDoom / EDGE / Legacy / ...
↓
GZDoom / modern ports
↓
современные standalone games
```

И эта ветка живёт до сих пор.

## 12. Как из Doom source ports возникла отдельная линия ZDoom → GZDoom?

ZDoom — один из главных случаев, когда source port постепенно превращается в полноценную игровую платформу.

Цепочка:

```text
Linux Doom source — 1997
        │
        ├── ранние Windows/source-port идеи
        ▼
      ZDoom — 1998
        │
        ├── Boom features
        ├── Hexen format
        ├── ACS
        ├── Heretic / Hexen / Strife support
        ├── DECORATE
        └── огромный modding API
                 │
                 ▼
             GZDoom — 2005
                 │
                 ├── hardware renderer
                 ├── 3D floors
                 ├── dynamic lights
                 ├── models
                 ├── portals
                 ├── ZScript
                 └── standalone games
```

ZDoom появляется практически сразу после открытия исходников. Первые публичные версии выходят в 1998 году.

Изначально задача вполне понятная:

```text
Doom
+
современный Windows
+
нормальный звук
+
мышь
+
новые разрешения
```

Но уже к 1999 году ZDoom имеет:

- freelook;
- высокие разрешения;
- translucency;
- console;
- Quake-style bindings;
- jumping;
- crosshair;
- улучшенный z-clipping;
- Hexen map format;
- Boom functionality.

То есть всего за пару лет он начинает объединять несколько разошедшихся ветвей Doom-family.

### ZDoom собирает дерево обратно

В коммерческую эпоху:

```text
Doom
├── Heretic
├── Hexen
└── Strife
```

В source-port эпоху:

```text
Doom
Heretic
Hexen
Strife
Boom
  \ | | /
   ZDoom
```

Особенно важен Hexen.

Именно от Raven ZDoom получает/развивает идеи:

- ACS;
- parameterized specials;
- TID;
- polyobjects;
- более сложную вертикальность;
- richer world logic.

Теперь мод для Doom II может использовать архитектурные идеи, придуманные для Hexen.

### DECORATE

Настоящий перелом — постепенный вынос gameplay definitions из C++ движка.

Оригинальный Doom:

```text
monster behavior
weapon behavior
item behavior
=
C tables/functions
```

ZDoom вводит DECORATE-подобную модель:

```text
ACTOR MyMonster
{
    Health 500
    Speed 12

    States
    {
    Spawn:
        ...
    See:
        ...
    Missile:
        ...
    }
}
```

Теперь моддер создаёт новых actors без собственного engine fork.

Появляется наследование:

```text
MyMonster : DoomImp
```

То есть игровые сущности начинают становиться классами.

### ACS расширяется

Hexen ACS был прежде всего level-scripting language.

ZDoom превращает его в большой gameplay/world scripting environment с огромным количеством engine functions.

Возникают два слоя:

```text
ACS
↓
логика карты / события
```

и:

```text
DECORATE
↓
actors / weapons / monsters
```

### Doom-мод перестаёт выглядеть как Doom

Когда можно заменить:

- weapons;
- monsters;
- player classes;
- HUD;
- menus;
- physics;
- scripts;
- maps;
- art;
- sound;

Doom IWAD постепенно становится просто базовым набором ресурсов.

Именно отсюда появляются проекты, которые уже почти являются самостоятельными играми.

### GZDoom

Главным ограничением ZDoom долго остаётся software renderer.

Graf Zahl создаёт hardware/OpenGL branch, и в 2005 году появляется GZDoom.

Изначальная формула:

```text
ZDoom gameplay/modding architecture
+
OpenGL renderer
=
GZDoom
```

Со временем GZDoom добавляет:

- hardware renderer;
- 3D floors;
- dynamic lights;
- models;
- advanced portals;
- skyboxes;
- shaders;
- современный GPU pipeline.

Долгое время GZDoom остаётся дочерним fork'ом ZDoom и регулярно подтягивает upstream changes.

### ZScript

Следующий большой скачок.

DECORATE — definition language с states/action functions.

ZScript уже гораздо ближе к полноценному языку разработки gameplay:

- classes;
- inheritance;
- methods;
- variables;
- types;
- virtual functions;
- events;
- arrays;
- custom logic.

В какой-то момент сам стандартный gameplay GZDoom начинает частично определяться через ZScript.

Это очень важная инверсия:

```text
раньше:
game logic = engine C code

теперь:
engine
 ↓
generic runtime
 ↓
ZScript classes
 ↓
game
```

### Конец оригинального ZDoom

В 2017 разработка оригинального ZDoom прекращается.

После этого GZDoom из дочернего hardware fork становится фактическим главным продолжателем архитектурной линии.

Итого:

```text
Doom
 ↓
source
 ↓
ZDoom
 ↓
GZDoom
 ↓
современная engine platform
```

GZDoom уже нельзя адекватно описывать просто как «порт Doom на новую ОС».

Это отдельное engine family, сохранившее глубокую Doom-совместимость.

## 13. Насколько далеко GZDoom сегодня ушёл от оригинального Doom engine?

Очень далеко.

По происхождению:

```text
Doom
 ↓
ZDoom
 ↓
GZDoom
```

По возможностям современный GZDoom уже разумнее считать самостоятельным движком с Doom-compatible архитектурной ДНК.

### World model

Самая сильная связь с Doom сохраняется в понятиях:

```text
sector
linedef
sidedef
vertex
actor
state
WAD/lump ancestry
```

Но современный sector уже способен иметь:

- slopes;
- 3D floors;
- portals;
- fog;
- extended lighting/color properties;
- дополнительные planes.

Оригинальный Doom:

```text
floor  ─────────
ceiling─────────
```

GZDoom может создавать значительно более сложные вертикальные структуры.

### 3D floors

Doom фундаментально ограничен одним floor/ceiling на sector.

GZDoom позволяет строить дополнительные 3D floors, фактически имитируя/реализуя многослойные пространства.

Это ломает одно из центральных ограничений id Tech 1.

### Portals

Line/sector portals позволяют строить топологию, которую оригинальный Doom вообще не мог представить.

### Renderer

Здесь расстояние максимальное.

Doom:

```text
CPU
↓
software renderer
↓
8-bit palette
↓
320×200
```

GZDoom:

```text
GPU
↓
OpenGL / Vulkan
↓
true color
↓
dynamic lights
↓
shaders
↓
models / voxels
↓
arbitrary modern resolutions
```

При этом software renderer тоже не исчез полностью — он сам эволюционировал.

### Lighting

Оригинальный Doom:

```text
sector.lightlevel
```

Современный GZDoom:

- dynamic lights;
- attached lights;
- colored lighting;
- shader-based effects;
- modern material/postprocessing paths.

### Actor system

Doom:

```text
mobjinfo[]
states[]
```

GZDoom:

```text
class DoomImp : Actor
```

Игровые сущности теперь имеют:

- inheritance;
- methods;
- properties;
- states;
- virtual functions;
- event hooks.

Это уже полноценная объектная gameplay architecture.

### ZScript

ZScript делает GZDoom практически scripting-oriented game engine.

Моддер способен писать собственные игровые системы, не меняя C++ движка.

### UDMF

Оригинальный Doom map format — набор бинарных lumps.

GZDoom поддерживает UDMF — текстовый Universal Doom Map Format с огромным количеством дополнительных свойств geometry/entities.

### Поддержка всего семейства

GZDoom переваривает:

- Doom;
- Doom II;
- Heretic;
- Hexen;
- Strife;
- Chex Quest;
- Boom/MBF-derived extensions.

Разошедшиеся в 1990-х ветви в итоге снова сходятся в одном runtime.

### Standalone games

Самый важный рубеж:

```text
GZDoom
+
собственные resources
+
свой ZScript
+
свои maps
=
самостоятельная игра
```

Оригинальный Doom IWAD вообще не обязателен.

### Что осталось от Doom?

Условно:

| Слой | Наследство Doom |
|---|---|
| Sector/linedef concepts | сильное |
| Actor/state concepts | сильное происхождение |
| Original behavior compatibility | намеренно сохранено |
| Resource/lump ancestry | сильное |
| Gameplay implementation | сильно обобщено |
| Scripting | практически новое |
| Renderer | практически другой мир |
| Platform layer | современный |
| Tool ecosystem | пост-Doom |

Поэтому вопрос «сколько процентов оригинального Doom-кода осталось?» почти бесполезен.

Важнее:

> сохраняется ли архитектурная генеалогия?

Да.

### Хорошая аналогия

GZDoom похож на город, построенный поверх древнего города.

Фундаментальные улицы:

```text
sector
linedef
actor
state
tic
WAD
```

ещё узнаваемы.

Но сверху выросли:

```text
C++
OpenGL
Vulkan
3D floors
slopes
portals
models
dynamic lights
shaders
UDMF
ACS
DECORATE
ZScript
standalone games
```

Поэтому GZDoom уже самостоятельный современный движок, но с очень глубокой Doom-совместимой архитектурой.

## 15. Кому id лицензировала первый Quake engine?

Здесь важно различить:

- кто одним из первых получил лицензию;
- какая самостоятельная сторонняя игра первой реально вышла.

### Valve

Valve — один из самых ранних и лучше всего документированных внешних лицензиатов Quake engine.

В 1996 году, практически сразу после основания, Gabe Newell и Mike Harrington лицензируют Quake technology.

Причина проста:

```text
есть деньги
+
есть опыт software development
+
есть идея новой FPS
-
нет современного 3D engine
```

Valve сознательно решает не тратить первые годы на повторное изобретение:

- renderer;
- BSP;
- networking;
- collision;
- tools.

Вместо этого ресурсы можно вложить в:

- AI;
- narrative;
- animation;
- scripted sequences;
- interaction.

### Michael Abrash

Ключевой посредник — Michael Abrash.

Он работал с Harrington в Microsoft, затем ушёл в id и помогал Кармаку с Quake.

Именно Abrash убедил будущую Valve, что Quake technology — правильная стартовая точка, а перед id поручился за Newell/Harrington.

Схема:

```text
Microsoft
   │
   ├── Harrington
   ├── Newell
   └── Abrash
          │
          ▼
      id Software
          │
      Quake engine
          │
          ▼
        Valve
```

Valve приезжает к id и получает доступ к Quake source.

### Raven

Raven также становится одним из важнейших ранних пользователей технологии:

```text
Quake
 ↓
Hexen II
```

Hexen II 1997 года — первая крупная самостоятельная сторонняя игра, которую уверенно можно поставить как коммерческий релиз непосредственно на модифицированном Quake engine.

### Почему Valve важнее для генеалогии

Raven:

```text
Quake
↓
серьёзно модифицируем
↓
Hexen II
```

Valve:

```text
Quake
↓
fork
↓
переписываем
↓
ещё переписываем
↓
GoldSrc
```

Именно второй тип порождает долгоживущее engine family.

Поэтому в истории Quake licensing две ранние линии особенно важны:

```text
                  QUAKE
                    │
       ┌────────────┴─────────────┐
       │                          │
     Raven                       Valve
       │                          │
   Hexen II                    Half-Life
                                  │
                               GoldSrc
                                  │
                               Source
                                  │
                              Source 2
```

## 16. Как Raven модифицировала Quake engine для Hexen II?

Hexen II — первый момент, когда Raven переносит собственную дизайн-философию уже на настоящий 3D-engine.

С Doom-era линией происходит разрыв:

```text
Doom → Heretic → Hexen
```

заканчивается.

Новая линия:

```text
Quake
↓
Raven fork
↓
Hexen II
```

### Что Quake уже давал

- настоящий polygonal 3D;
- 3D models;
- BSP;
- lightmaps;
- свободный pitch камеры;
- полноценную XYZ collision;
- networking;
- QuakeC.

То есть Raven больше не нужно изобретать фальшивую вертикальность поверх 2.5D.

### QuakeC → HexenC

Quake:

```text
C engine
  ↓
QuakeC VM
  ↓
progs.dat
```

Raven сохраняет эту архитектуру, но расширяет game code под свои задачи. Эту ветку обычно называют HexenC.

Сюда уходят:

- classes;
- weapons;
- AI;
- XP;
- abilities;
- inventory;
- puzzle logic;
- RPG stats.

### Player classes

Hexen II имеет:

- Paladin;
- Crusader;
- Assassin;
- Necromancer.

И это разные игровые archetypes с собственными оружием и параметрами.

### XP / level system

Quake:

```text
нашёл оружие
↓
следующая карта
```

Hexen II:

```text
убил врага
↓
получил XP
↓
level up
↓
health/mana/stat growth
↓
ability unlock
```

Это уже persistent RPG character state.

### Inventory

Возвращается Raven-модель переносимых artifacts и puzzle items.

```text
pickup
↓
inventory
↓
use later
```

### Hubs

Raven заново строит над Quake hub system:

```text
Map A ↔ Map B ↔ Map C
```

Состояние игрока и puzzle progression переходит между картами.

Это снова превращает серию в приключенческую структуру, а не линейный Quake episode.

### Более интерактивный 3D-мир

Quake позволяет Raven естественно делать то, что было тяжело на Doom:

- destructible objects;
- более физическую архитектуру;
- вертикальные пространства;
- polygonal monsters;
- melee в настоящем 3D;
- mounted/interactable mechanisms.

### Melee

В Quake axe — вспомогательное оружие.

В Hexen II некоторые классы строятся вокруг ближнего боя, поэтому приходится серьёзнее работать с:

- range;
- damage;
- animation;
- class modifiers;
- reactions.

### Production pipeline

Команда Raven должна была полностью переучиваться.

В Doom эпоху:

```text
2D/2.5D mapper thinking
```

В Quake:

```text
brushes
true 3D
BSP
lightmaps
polygonal models
collision hulls
```

Это уже смена способа производства игры.

### HexenWorld

Raven также строит собственную сетевую ветку поверх QuakeWorld:

```text
QuakeWorld
↓
HexenWorld
↓
Siege
```

То есть Hexen II породил ещё и отдельную multiplayer-ветку Quake technology.

### Итог

Hexen II не переписывает Quake renderer радикально.

Низкоуровневый фундамент остаётся id.

Raven вкладывается прежде всего в:

```text
Quake foundation
+
HexenC
+
classes
+
RPG progression
+
inventory
+
hub state
+
interactive fantasy gameplay
```

Это очень типичный Raven-паттерн:

> брать передовой low-level engine id и строить сверху гораздо более сложную игровую систему.

## 17. Какие ещё коммерческие игры непосредственно использовали Quake engine?

У Quake нужно разделять:

```text
1. самостоятельные engine forks
2. официальные mission packs
3. коммерческие total conversions
```

### Hexen II

Главный самостоятельный внешний fork:

```text
Quake
↓
Raven
↓
Hexen II
↓
Portal of Praevus
```

### Scourge of Armagon

Официальный mission pack от Hipnotic Interactive.

Технологически:

```text
Quake
+
новые maps
+
новые monsters
+
новый QuakeC gameplay
```

а не отдельный engine family.

### Dissolution of Eternity

Аналогичный официальный mission pack от Rogue Entertainment.

### Malice

Коммерческий total conversion.

Он почти полностью заменял:

- levels;
- enemies;
- models;
- weapons;
- HUD;
- art;
- world.

Но требовал установленный Quake.

То есть:

```text
QUAKE.EXE
+
Malice data
+
QuakeC
=
Malice
```

Это почти самостоятельная игра по контенту, но не отдельный engine executable.

### Shrak

Ещё один коммерческий Quake TC:

- новые уровни;
- враги;
- weapons;
- grappling hook;
- gameplay features;
- CTF.

Тоже требовал зарегистрированный Quake.

### X-Men: The Ravages of Apocalypse

Коммерческий X-Men total conversion:

- новые maps;
- models;
- enemies;
- Marvel IP;
- QuakeC behavior.

И опять — нужен Quake.

### Abyss of Pandemonium

Большое коммерческое дополнение/TC, также живущее поверх Quake technology.

### Поздние бюджетные игры

Даже после Quake II/III первый Quake engine продолжает жить.

Примеры:

- Laser Arena;
- CIA Operative: Solo Missions;
- Eternal War: Shadows of Light.

Часть поздних проектов уже появляется в эпоху GPL и поэтому существует в другой юридической модели.

### Почему коммерческих TC было так много?

Потому что Quake одновременно дал:

```text
современный 3D engine
+
QuakeC
+
редакторы
+
заменяемые assets
+
огромную аудиторию
```

Небольшой команде было намного реалистичнее сделать коммерческий Quake TC, чем писать собственный 3D-engine.

### Что сюда не относится напрямую

**Half-Life** — уже глубокий потомок Quake через GoldSrc.

**Daikatana** начиналась на Quake, но финальная технология переехала на Quake II branch.

### Главное

Сам список игр на непосредственном Quake engine относительно небольшой.

Но историческая важность Quake не в количестве прямых лицензиатов.

Она в том, что:

```text
Quake
├── Raven → Hexen II
├── community source ports
├── DarkPlaces
└── Valve → GoldSrc → Source → Source 2
```

То есть один engine стал корнем нескольких самостоятельных семейств.

## 18. Как Valve получила Quake engine для разработки Half-Life?

Valve получила Quake engine благодаря сочетанию трёх вещей:

```text
деньги основателей
+
личные связи с id
+
Michael Abrash
```

### Старт Valve

В 1996 году Gabe Newell и Mike Harrington уходят из Microsoft и основывают Valve.

У них есть собственное финансирование и software-engineering experience, но нет современного 3D-engine.

Писать одновременно:

- команду;
- игру;
- renderer;
- BSP;
- collision;
- networking;
- tools;

для новой студии слишком рискованно.

Поэтому решение рациональное:

```text
не писать Quake заново
↓
лицензировать Quake
↓
сфокусироваться на том,
что сделает Half-Life новой игрой
```

### Michael Abrash

Abrash — ключевой мост.

Он был связан с Microsoft, затем ушёл в id и работал над Quake вместе с Кармаком.

Именно он:

- объясняет будущей Valve ценность Quake technology;
- знакомит стороны;
- фактически поручается за Newell и Harrington.

Без него id вполне могла не дать свою новейшую технологию неизвестной студии без единого релиза.

### Поездка в id

Valve приезжает в Техас.

Атмосфера не была романтической.

Для id это не «будущие создатели Half-Life», а несколько бывших сотрудников Microsoft. Но рекомендация Abrash и серьёзный инженерный background помогают заключить сделку.

Valve уезжает с **Quake source code**.

Это принципиально:

```text
не:
закрытая engine DLL

а:
исходный код
```

Поэтому команда может свободно перестраивать технологию.

### Лицензия как доверие для издателя

Для Sierra новая Valve выглядела намного серьёзнее благодаря комбинации:

```text
бывшие Microsoft engineers
+
собственное финансирование
+
Quake license
+
работающий 3D фундамент
```

То есть Quake license была не только технологией, но и credibility.

### Quake II миф

GoldSrc не является 50/50 смесью Quake 1 и Quake II.

Основной фундамент — Quake 1.

Из QuakeWorld/Quake II lineage Valve брала отдельные fixes/routines, когда Кармак уже решил конкретную техническую проблему.

Схема:

```text
              QUAKE 1
                 │
                 ▼
             Valve fork
                 │
      ┌──────────┼───────────┐
      │          │           │
 Valve code   QW ideas   отдельные
                         Q2 routines
      │          │           │
      └──────────┼───────────┘
                 ▼
              GoldSrc
```

### Главное

Одна лицензия 1996 года запускает:

```text
Quake
↓
Half-Life engine
↓
GoldSrc
↓
Source
↓
Source 2
```

То есть маленькая сделка id с новой студией становится началом тридцатилетнего технологического семейства Valve.

## 19. Сколько Quake осталось в финальном GoldSrc?

Никакого честного процента вида «40% Quake» не существует.

Нужно смотреть по подсистемам.

### BSP / world representation

Здесь Quake-наследство очень сильное.

Quake:

```text
.map
↓
QBSP
↓
BSP
↓
PVS
```

GoldSrc:

```text
.map
↓
CSG/BSP
↓
VIS
↓
RAD
↓
.bsp
```

Сам world model всё ещё строится вокруг:

- brushes;
- BSP tree;
- leaves;
- faces;
- clipnodes;
- PVS.

GoldSrc BSP v30 — прямой родственник Quake BSP v29.

### Renderer

Core rendering architecture тоже остаётся очень Quake-derived:

```text
BSP
↓
visible surfaces
↓
base texture
×
lightmap
```

Но Valve серьёзно расширяет presentation.

Главное изменение — RGB lighting/color lightmaps вместо более простой Quake lighting representation.

### Textures/resources

Quake:

```text
WAD2
```

GoldSrc:

```text
WAD3
```

Опять эволюция, а не новый мир.

### Brush-based level design

Half-Life maps остаются Quake-family brush worlds.

Это одна из самых сильных архитектурных связей.

### Animation

А вот здесь серьёзный разрыв.

Quake:

```text
vertex animation
```

GoldSrc:

```text
skeletal animation
+
Studio Model
```

Valve создаёт собственный character pipeline:

- bones;
- animation sequences;
- attachments;
- controllers;
- body groups.

### Game logic

Ещё сильнее.

Quake:

```text
engine
↓
QuakeC VM
↓
progs.dat
```

Half-Life:

```text
engine
↓
native C++ Game DLL
```

QuakeC выбрасывается.

### AI

Half-Life AI практически новая система.

Quake:

```text
see player
↓
chase
↓
attack
```

Half-Life нужны:

- scientists;
- Barney;
- marines;
- squads;
- schedules;
- tasks;
- scripted behavior;
- speech;
- relationships.

Именно AI — один из слоёв, где Half-Life сильнее всего перестаёт быть Quake.

### Entity concept

При этом идея entities сохраняется.

Quake:

```text
"classname" "monster_ogre"
```

Half-Life:

```text
"classname" "monster_scientist"
"targetname" "..."
```

Базовая модель:

```text
BSP world
+
key/value entities
```

живёт.

### Decals / beams / audio

Valve добавляет новые presentation systems:

- bullet marks;
- blood/scorch decals;
- beams;
- значительно более богатый sound/dialogue layer.

### Networking

На релизе Half-Life networking всё ещё очень сильно Quake/QuakeWorld-derived.

Позже Valve серьёзно переписывает его, поэтому GoldSrc начала 2000-х дальше от Quake, чем GoldSrc 1998 года.

### Quake II вклад

Небольшой:

- отдельные fixes;
- PAS/Winsock-related routines;
- отдельные полезные решения.

Но не второй фундамент движка.

### Условная таблица

| Подсистема | Наследство Quake |
|---|---|
| BSP / world | очень сильное |
| map pipeline | очень сильное |
| PVS | очень сильное |
| core renderer | очень сильное |
| lighting | Quake-база + крупные изменения |
| entity concept | сильное |
| networking 1998 | очень сильное Q/QW |
| поздний networking | намного больше Valve |
| gameplay | сильно Valve |
| AI | почти полностью Valve |
| skeletal animation | Valve |
| Studio models | Valve |
| decals | Valve |
| QuakeC | выброшен |
| C++ Game DLL | Valve |

GoldSrc можно представить как:

```text
┌─────────────────────────────┐
│       HALF-LIFE / VALVE     │
│ AI                          │
│ C++ gameplay                │
│ skeletal animation          │
│ NPC / scripted sequences    │
│ decals / richer audio       │
├─────────────────────────────┤
│         QUAKE DNA           │
│ BSP                         │
│ brush world                 │
│ PVS                         │
│ renderer architecture       │
│ map pipeline                │
│ network ancestry            │
└─────────────────────────────┘
```

Поэтому одновременно верны две фразы:

> Half-Life работает на глубоко модифицированном Quake engine.

и:

> GoldSrc уже самостоятельный движок Valve.

## 20. Как Quake engine превратился в GoldSrc?

Не было одного момента, когда Valve «переключилась» с Quake на GoldSrc.

GoldSrc возник постепенно во время разработки Half-Life.

```text
Quake
  │
  │ 1996: лицензия
  │
  ├── новый gameplay layer
  ├── новый AI
  ├── skeletal animation
  ├── Studio Models
  ├── colored lighting
  ├── decals
  ├── sound extensions
  ├── scripted sequences
  ├── новые tools
  └── network changes
  │
  ▼
Half-Life engine
  │
  ▼
GoldSrc
```

### Сначала Valve получает рабочий Quake

Это позволяет с первого дня строить игру, а не сначала несколько лет писать renderer.

Игра и движок эволюционируют одновременно.

### Quake game layer не подходит

Half-Life требует:

```text
непрерывное приключение
NPC
scripted scenes
диалоги
AI
environmental storytelling
```

Поэтому Valve отказывается от QuakeC и делает native C++ Game DLL architecture.

Это один из главных разрывов.

### Entity architecture растёт

Quake уже дал:

```text
world
+
entities
+
key/value
```

Valve превращает это в огромное семейство:

```text
monster_scientist
monster_human_grunt
func_door
func_train
func_breakable
trigger_once
scripted_sequence
env_beam
...
```

Так появляется язык сцен и взаимодействий Half-Life без отдельного scripting language.

### Scripted sequences через entities

Вместо ACS:

```text
script { ... }
```

Half-Life строит сцену через:

```text
trigger
↓
targetname / target
↓
scripted_sequence
↓
NPC / door / explosion
```

Это своего рода data-driven visual scripting до появления собственно visual scripting.

### Новый AI

Quake monster AI недостаточен.

Valve строит schedule/task-like модель NPC, способную обслуживать:

- союзников;
- squads;
- cover;
- speech;
- scripted behavior;
- reactions.

### Skeletal animation

Quake vertex animation плохо подходит для человеческих персонажей и большого количества анимаций.

Valve переходит к skeleton/bones/sequences.

Отсюда появляется Studio Model pipeline.

### Renderer расширяется, но не выбрасывается

BSP/lightmap foundation сохраняется.

Добавляются:

- RGB lighting;
- новые surface effects;
- decals;
- дополнительные rendering paths.

### Sound превращается в narrative infrastructure

Half-Life требуется:

- NPC speech;
- PA announcements;
- machinery;
- scripted sound;
- ambient storytelling.

Audio становится частью режиссуры.

### Worldcraft

Valve покупает Worldcraft — редактор, изначально выросший вокруг Quake.

Дальше:

```text
Quake editing
↓
Worldcraft
↓
Half-Life Worldcraft
↓
Hammer
```

То есть GoldSrc наследует от Quake не только runtime, но и культуру brush/BSP level design.

### Networking

Сначала — сильная Quake/QuakeWorld база.

Затем Valve постепенно перестраивает её под собственные игры.

### Название GoldSrc появляется поздно

Во время разработки это был просто **Half-Life engine**.

Перед релизом кодовую базу разделяют:

```text
$/Goldsrc
```

— стабильная shipping branch,

и:

```text
$/Src
```

— ветка следующих экспериментов.

Отсюда и появляются названия:

```text
GoldSrc
```

и позднее:

```text
Source
```

То есть название GoldSrc фактически ретроспективное: сам движок уже почти сформирован, когда это имя становится полезным.

### Итоговая миграция

```text
QUAKE
│
├── BSP/world ───────────────► сохранён и расширен
├── PVS ─────────────────────► сохранён
├── renderer ────────────────► расширен
├── QuakeC ──────────────────► удалён
│                               C++ DLL
├── monster AI ──────────────► переписан
├── vertex models ───────────► skeletal Studio Models
├── entity logic ────────────► huge Valve entity system
├── sound ───────────────────► расширен
├── editor ecosystem ────────► Worldcraft/Hammer
└── networking ──────────────► сначала Q/QW, затем Valve
```

GoldSrc возник не через rewrite-from-scratch.

Он возник через **селективную эволюцию**:

> работающий Quake subsystem оставляем; мешающий Half-Life subsystem заменяем.

Именно поэтому Valve смогла одновременно сохранить зрелый низкоуровневый фундамент и построить совершенно новую по характеру игру.

## 21. Как GoldSrc постепенно превратился в Source?

Source не появился как полностью новый пустой проект. Он вырос из той самой экспериментальной ветки `Src`, которая отделилась от shipping-ветки Half-Life.

Генеалогически:

```text
Quake
  ↓
GoldSrc
  ↓
Src branch
  ↓
массовая замена подсистем
  ↓
Source
```

Но это не означает, что Half-Life 2 использует «Quake с патчами». К 2004 году Valve заново построила или радикально заменила огромную часть ключевых runtime systems.

### Source сначала распался на ветки ещё внутри первого поколения

Source не был одной аккуратной версией:

```text
Source 1.0
Source 1.1
Source 1.2
```

Valve постоянно форкала его под игры:

```text
Source 2004
   ↓
Source 2006
   ↓
Orange Box
   ↓
Left 4 Dead
   ↓
Left 4 Dead 2
   ↓
Alien Swarm
   ↓
Portal 2
   ↓
CS:GO / Dota-era branches
```

Каждая команда развивала собственную ветку.

Но фундамент Source формируется во время разработки Half-Life 2.

### World representation всё ещё выдаёт Quake/GoldSrc

Source по-прежнему строит основную structural geometry вокруг:

```text
brushes
↓
VBSP
↓
BSP
↓
VVIS
```

Это одна из самых сильных линий наследства.

Hammer 4 — прямое продолжение Hammer/Worldcraft.

То есть level designer всё ещё мыслит:

```text
brush world
+
entities
+
compile
```

### Но мир становится гибридным

GoldSrc:

```text
WORLD ≈ BSP geometry + models
```

Source:

```text
WORLD =
BSP structural skeleton
+
props
+
displacements
+
dynamic physics objects
+
detail geometry
```

Displacements позволяют строить более органичный terrain, а models/props перестают быть вспомогательным исключением.

### Renderer фактически новый

Valve строит shader-oriented rendering pipeline:

- HLSL;
- bump/normal mapping;
- cubemaps;
- reflections;
- refraction;
- advanced water;
- dynamic lighting;
- projected shadows;
- particles;
- fog;
- 3D skyboxes;
- Radiosity Normal Mapping.

Здесь родство с Quake уже скорее историческое, чем функциональное.

### Texture → Material

Это один из важнейших архитектурных скачков.

GoldSrc:

```text
surface
↓
texture
```

Source:

```text
surface
↓
material
```

Material описывает уже не только изображение, но:

- shader;
- texture;
- физические свойства;
- звук взаимодействия;
- friction;
- density;
- break behavior.

То есть rendering, physics и audio начинают говорить об объекте на общем языке materials.

### Physics

GoldSrc имел обычную FPS physics/collision model.

Half-Life 2 требует:

- rigid bodies;
- constraints;
- ragdolls;
- vehicles;
- ropes;
- mass;
- friction;
- buoyancy.

Valve интегрирует Havok и строит вокруг него собственный gameplay layer.

Главное: физика становится **геймплеем**, а не декоративным эффектом.

```text
доска + кирпич
→ рычаг

бочка
→ плавучесть

радиатор
→ щит

sawblade
→ оружие

Gravity Gun
→ центральная механика
```

### Animation

GoldSrc уже имел skeletal animation, но Source строит гораздо более сложную actor system:

- layered animation;
- blending;
- pose parameters;
- procedural controllers;
- facial flexes;
- eye tracking;
- body/face coordination.

Это уже система для персонажа-актёра.

### Facial animation / Faceposer

Появляется отдельный choreography pipeline:

```text
dialogue
+
phonemes
+
facial flexes
+
eyes
+
gestures
+
body animation
```

Именно поэтому Alyx и другие персонажи Half-Life 2 способны играть сцену в реальном времени.

### scripted_sequence → choreography

GoldSrc связывает сцену через entities.

Source сохраняет философию «события происходят в мире», но даёт гораздо более мощный режиссёрский инструментарий.

### Entity I/O

GoldSrc:

```text
target
targetname
```

Source:

```text
entity
├── Inputs
├── Outputs
├── parameters
└── delays
```

Например:

```text
button.OnPressed
 ├→ door.Open
 ├→ light.TurnOff
 └→ speaker.PlaySound
```

Это уже полноценный event graph.

### AI

Для Half-Life 2 AI тоже серьёзно перестраивается.

Нужны:

- interaction с physics;
- companions;
- choreography;
- более динамичный world state;
- richer navigation/behavior.

### Networking

Конкретная реализация меняется, но инженерная линия QuakeWorld → GoldSrc → Counter-Strike даёт Valve огромный опыт prediction, interpolation, lag compensation и client/server architecture.

### Tools

Это одна из самых непрерывных линий:

```text
Quake editors
↓
Worldcraft
↓
GoldSrc Hammer
↓
Source Hammer 4
```

Даже map compile pipeline сохраняет древнюю форму:

```text
GoldSrc:
.map
↓
CSG/BSP
↓
VIS
↓
RAD

Source:
.vmf
↓
VBSP
↓
VVIS
↓
VRAD
```

### Итог

Source — классический корабль Тесея.

Он исторически вырос из GoldSrc, но к 2004 году уже имеет:

- новый renderer;
- новый material system;
- современную physics integration;
- новый actor/animation pipeline;
- facial system;
- choreography;
- новый AI;
- новый network stack;
- сильно развитые tools.

Поэтому:

```text
GoldSrc → Source
```

— это одновременно **прямая генеалогия** и **настоящее новое поколение**.

## 22. Насколько Source можно считать дальним потомком Quake, а не полностью новым движком?

Source корректно считать прямым дальним потомком Quake **по генеалогии codebase**.

Но Source 2004 года уже совершенно нормально считать самостоятельным движком Valve по возможностям и архитектурной идентичности.

Ключ:

```text
«потомок Quake»
≠
«Quake с кучей патчей»
```

### Самое сильное доказательство — ветвление GoldSrc/Src

Source исторически начинается как branch существующего Half-Life codebase:

```text
Half-Life codebase
        │
   ┌────┴────┐
   │         │
GoldSrc     Src
   │         │
shipping   future experiments
             │
             ▼
           Source
```

То есть генеалогическая линия документирована напрямую.

### Кармак сам говорил о Quake-коде в Half-Life 2

В 2004 году Джон Кармак отмечал, что в Half-Life 2 всё ещё существуют фрагменты раннего Quake code.

Это не значит:

> Half-Life 2 работает на Quake engine.

Но подтверждает, что continuity была не только концептуальной: отдельное прямое кодовое наследство действительно пережило годы разработки.

### Что осталось архитектурно

#### BSP/brush model

```text
Quake
↓
brushes
↓
BSP
↓
GoldSrc
↓
Source
```

Source всё ещё компилирует structural world через VBSP/VVIS.

#### Hammer lineage

```text
Worldcraft
↓
GoldSrc Hammer
↓
Source Hammer
```

#### Entity philosophy

Quake:

```text
BSP world
+
key/value entities
```

Source:

```text
BSP world
+
entities
+
Inputs/Outputs
```

То есть сама authoring-модель развивается, а не заменяется чужой.

### Что уже практически новое

- renderer;
- physics;
- facial system;
- advanced animation;
- AI;
- material pipeline;
- networking implementation;
- audio.

Поэтому бессмысленно говорить:

> Source renderer — это Quake renderer.

Нет.

Но:

> Source является прямым потомком движка, который Valve когда-то форкнула из Quake.

Да.

### Три типа наследства

| Тип | Пример |
|---|---|
| Прямая codebase genealogy | Quake → GoldSrc → Src → Source |
| Архитектурное наследство | BSP, brushes, entities |
| Tool lineage | Worldcraft → Hammer |
| Сильно переписанные systems | renderer, networking, AI |
| Практически новые systems | facial/choreography, modern physics stack |

### Можно ли сказать, сколько процентов Quake осталось?

Нет.

Полный Source proprietary, а публичный SDK не равен полному историческому repository.

Цифры вроде:

```text
Source = 10% Quake
```

— гадание.

Точная формулировка:

> Source — самостоятельный движок Valve, возникший путём многолетней эволюции GoldSrc, который, в свою очередь, является глубоким форком Quake. Поэтому Source — прямой дальний потомок Quake по кодовой и архитектурной генеалогии, но уже не разумно описывается как просто «модифицированный Quake engine».

## 23. Как линия продолжилась от Source к Source 2?

Source 2 снова появляется через эволюцию, а не через магический rewrite за одну ночь.

Но разрыв с предшественником здесь уже намного сильнее.

```text
Source
  │
  ├── Orange Box
  ├── Left 4 Dead
  ├── Alien Swarm
  ├── Portal 2
  ├── Dota 2
  │
  ▼
накопленный technical debt
  │
  ▼
новый renderer
новая physics
новые resources
новые tools
новый UI
новый audio
  │
  ▼
SOURCE 2
```

### Source сам распался на множество project branches

Разные игры получают свои варианты Hammer, runtime и toolchain.

Старые maps/assets начинают хуже переноситься между ветками.

Это признак того, что единый фундамент всё тяжелее поддерживать.

### Главная цель Source 2 — productivity

При публичном анонсе Valve особенно подчёркивала не «больше полигонов», а:

> повысить производительность авторов контента.

Это очень важная философия Source 2.

Проблема старого Source уже не только в renderer.

Проблема:

```text
современный контент
↓
старый pipeline
↓
дорогая iteration
```

### Dota 2 Reborn

Первый большой production-test Source 2.

Valve не выпускает отдельную технологическую демку.

Она пересаживает огромную живую service-game:

```text
Dota 2 / Source
↓
полная миграция
↓
Dota 2 Reborn / Source 2
```

Это отличный стресс-тест новой архитектуры.

### Новые asset formats

Source:

```text
.vmf
.vmt
.mdl
```

Source 2:

```text
.vmap
.vmat
.vmdl
```

и runtime compiled versions:

```text
.vmap_c
.vmat_c
.vmdl_c
```

Старые assets требуют импорта/конвертации.

Это уже настоящий generational break.

### Новый Hammer

Source 2 Hammer становится не просто brush editor:

- 3D mesh editing;
- asset browser;
- drag-and-drop;
- live lighting;
- modern preview;
- более integrated authoring.

### Уход от ancient convex-brush worldview

Quake/GoldSrc/Source долго жили вокруг:

```text
world
=
convex brushes
→ BSP
```

Source 2 позволяет строить complex mesh geometry без старой фундаментальной зависимости от convex brush architecture.

Это один из самых символических разрывов с Quake lineage.

### Новый renderer

Source 2 получает современный GPU-oriented rendering stack:

- больше batches;
- complex meshes;
- modern lighting;
- normal mapping;
- более современную graphics API architecture;
- Vulkan support.

### Rubikon physics

Source 1 тесно связан с Havok/VPhysics.

Source 2 переходит на собственный Valve rigid-body engine — Rubikon.

То есть:

```text
Source:
Valve runtime + Havok ancestry

Source 2:
Valve runtime + Valve physics
```

### Новый audio stack

Valve переписывает audio:

- multithreading;
- full-quality processing;
- более низкая latency;
- audio scripting;
- более удобный designer workflow.

### Panorama UI

Source 2 получает Panorama:

```text
XML-like layout
+
CSS-like styling
+
scripting
```

UI становится отдельным современным framework.

### Source Filmmaker и общий resource environment

SFM перестраивается под Source 2 и использует те же maps/models/particles/sounds, что и игра.

Это движение к общей integrated content environment.

### 64-bit

Source 2 окончательно становится современной 64-bit платформой.

### Проверки реальными продуктами

```text
Dota 2 Reborn
2015
↓
service/multiplayer
```

```text
Half-Life: Alyx
2020
↓
high-fidelity VR / physics / characters
```

```text
Counter-Strike 2
2023
↓
competitive FPS / networking / legacy migration
```

### Итог

Source 2 сохраняет Valve-идентичность:

- Hammer;
- entities;
- I/O;
- console;
- client/server thinking;
- data-driven authoring.

Но массово заменяет конкретные Source 1 implementations:

- renderer;
- physics;
- asset formats;
- resource pipeline;
- audio;
- UI;
- world authoring;
- tool internals.

Поэтому Source 2 уже совершенно оправданно является **новым поколением**.

## 24. Есть ли в Source 2 вообще техническая наследственность от Quake — или связь уже только историческая?

Да, техническая наследственность ещё есть, но здесь особенно важно разделить три вещи:

```text
1. генеалогия
2. архитектурные идеи
3. буквальный Quake-код
```

### Генеалогия

Уверенно:

```text
Quake
↓
GoldSrc
↓
Source
↓
Source 2
```

Source 2 вырос из Valve engine lineage.

### Архитектурная преемственность

Заметна в:

- entity-oriented world;
- key/value properties;
- targetname;
- Inputs/Outputs;
- console/cvars culture;
- client/server architecture;
- Hammer lineage;
- data-driven content.

Например Source 2 entities всё ещё имеют `targetname` и взаимодействуют через Inputs/Outputs.

Это очень длинная концептуальная линия:

```text
Quake entity
↓
GoldSrc entity
↓
Source entity + I/O
↓
Source 2 entity + I/O
```

### А вот древний BSP/brush фундамент уже не определяет всё

Source 2 освобождается от старого правила:

```text
structural world = convex brushes
```

и использует гораздо более современное mesh authoring.

Старые Source assets не runtime-compatible без conversion.

### Renderer

Практически новый мир:

```text
Quake renderer
↓
GoldSrc
↓
Source
↓
[большой разрыв]
↓
Source 2 renderer
```

### Physics

Тоже новая архитектура:

```text
Quake collision
↓
...
Source VPhysics/Havok
↓
Source 2 Rubikon
```

### Audio

Source 2 имеет новый audio system.

### Asset pipeline

Старые `.vmf/.vmt/.mdl` сменяются `.vmap/.vmat/.vmdl` и compiled resources.

### Что пережило Quake лучше всего?

Не конкретный renderer.

Не BSP format.

Не MDL.

А **модель разработки игры**:

```text
engine
+
world
+
entities
+
tools
+
data
```

и особенно:

```text
именованная entity
↓
связь с другой entity
↓
событие
↓
изменение мира
```

Идея оказывается долговечнее конкретной реализации.

### Прямой Quake-код?

Для Source/Half-Life 2 есть свидетельство Кармака о сохранившихся кусках раннего Quake code.

Для современного Source 2 такого публичного подтверждения нет.

Полный Source 2 repository закрыт.

Поэтому нельзя честно утверждать:

> в Counter-Strike 2 до сих пор лежит такой-то процент Quake source.

Это уже спекуляция.

### Итог

> Source 2 — дальний технический потомок Quake через непрерывную Valve lineage. Но большая часть характерных низкоуровневых систем Quake к этому поколению заменена. Прямое сохранение конкретного Quake code в Source 2 публично не доказано. Наследство наиболее уверенно видно в генеалогии, authoring model, entities, инструментах и инженерной культуре Valve.

## 25. Что произошло с оригинальным Quake engine после публикации исходников?

21 декабря 1999 года id Software публикует исходники Quake под GPL.

И открывает сразу несколько важных PC-веток:

- WinQuake;
- GLQuake;
- QuakeWorld;
- GLQuakeWorld.

После этого Quake перестаёт быть одним движком.

```text
                         QUAKE GPL
                            │
          ┌─────────────────┼─────────────────────┐
          │                 │                     │
   classic/mapper       graphics/engine       QuakeWorld/
       lineage             lineage            universal
```

### GPL сразу

В отличие от Doom, который сначала вышел под более ограниченной лицензией, Quake source идёт сразу в GPL-модель.

Это значит:

```text
берёшь source
↓
модифицируешь
↓
распространяешь
↓
соблюдаешь GPL
```

Кармак сознательно хотел, чтобы улучшения не исчезали в потерянных закрытых ветках.

### Standalone games разрешены моделью

Quake assets остаются proprietary.

Но:

```text
Quake source
+
свои maps
+
свои models
+
свои textures
+
свой game code
=
standalone game
```

Это открывает огромную дальнейшую ветку.

### NetQuake и QuakeWorld

Публикация сразу даёт сообществу две важные network lineages:

```text
NetQuake
↓
single-player / classic ports
```

и:

```text
QuakeWorld
↓
competitive multiplayer ports
```

### Classic preservation / modern Quake

Одна из важнейших линий:

```text
GLQuake
↓
FitzQuake
↓
QuakeSpasm
   ├── QuakeSpasm-Spiked
   ├── vkQuake
   └── Ironwail
```

Цель:

```text
Quake 1996 gameplay
+
современные ОС
+
современные разрешения
+
снятые limits
+
стабильность
```

QuakeSpasm фактически становится одной из основных baseline-платформ современной single-player mapping scene.

### Graphics/engine forks

Другая линия говорит:

> давайте использовать Quake как фундамент нового движка.

Главный пример — DarkPlaces.

```text
Quake
↓
DarkPlaces
↓
standalone games
```

### QuakeWorld ecosystem

Например:

```text
QuakeWorld
↓
FuhQuake
↓
ezQuake
```

и отдельно:

```text
QuakeWorld
↓
FTEQW
```

FTEQW затем станет намного универсальнее обычного QuakeWorld port.

### Vulkan / ray tracing

Открытая генеалогия позволяет менять даже graphics API:

```text
Quake
↓
QuakeSpasm
↓
vkQuake
↓
Vulkan
```

и экспериментировать с path/ray tracing.

То есть один family проходит:

```text
software
↓
OpenGL
↓
modern OpenGL
↓
Vulkan
↓
ray/path tracing experiments
```

### Source port превращается в engine fork

Ключевое различие:

```text
source port:
лучше запускает Quake
```

против:

```text
engine fork:
использует Quake как фундамент
для новых games/systems
```

DarkPlaces и FTEQW особенно важны именно как второй тип.

### QuakeC делает эту эволюцию легче

Оригинальный Quake уже разделяет:

```text
ENGINE
↓
QuakeC VM
↓
GAMEPLAY
```

Поэтому source port способен радикально менять renderer/networking, продолжая запускать старый game code.

Это даёт редкую долговечность модам.

### Quake как учебный материал

Публикация ещё и превращает Quake в один из важнейших открытых production-quality 3D engines для изучения:

- BSP;
- PVS;
- client/server;
- networking;
- collision;
- software/OpenGL rendering;
- QuakeC VM.

### Главное

Если бы source остался закрытым:

```text
Quake
↓
Quake II
↓
Quake III
↓
Quake 1 technology постепенно исчезает
```

После GPL:

```text
Quake
↓
source
↓
десятки forks
↓
современные ports
↓
standalone engines
↓
новые игры
```

Quake становится не старой версией движка, а **живой технологической генеалогией**.

## 26. Как появились QuakeSpasm, DarkPlaces, FTEQW и другие крупные форки?

После GPL не возникло одного community-engine.

Разработчики разошлись по совершенно разным философиям.

```text
                         Quake GPL
                            │
          ┌─────────────────┼─────────────────────┐
          │                 │                     │
      preserve          expand engine          network/
          │                 │                  universal
       FitzQuake          DarkPlaces             FTEQW
          │
     QuakeSpasm
          │
     ┌────┼───────────┐
     │    │           │
 Ironwail QSS      vkQuake
```

### FitzQuake

Цель:

```text
не сделать новый AAA-engine,
а сделать хороший современный Quake
```

Добавляются:

- современные resolutions;
- interpolation;
- fog;
- skyboxes;
- более высокие limits;
- улучшенный OpenGL;
- новые protocols.

Философия:

> Quake должен оставаться Quake.

### QuakeSpasm

Берёт FitzQuake и делает его современным кроссплатформенным фундаментом:

- 64-bit correctness;
- SDL;
- Windows/Linux/macOS;
- modern input/audio;
- bug fixes;
- portability.

QuakeSpasm становится особенно важным для single-player community.

### QuakeSpasm-Spiked

QSS добавляет в QuakeSpasm много идей FTE:

- расширенное networking;
- новые protocols;
- IPv6;
- downloads;
- voice chat;
- client-side QuakeC;
- MenuQC;
- расширенные builtins;
- новые formats;
- PK3;
- большие limits.

Идея:

```text
QuakeSpasm user experience
+
FTE-like capabilities
```

### Ironwail

Фокус:

```text
QuakeSpasm philosophy
+
максимальная performance
```

Современные community maps настолько огромны, что old-style renderer/runtime снова становится bottleneck.

Ironwail оптимизирует именно современный тяжёлый Quake-content.

### vkQuake

```text
QuakeSpasm/QSS ecosystem
+
Vulkan renderer
```

При этом gameplay и mod compatibility остаются Quake-derived.

### DarkPlaces

Совершенно другая философия.

Не:

```text
как сохранить Quake?
```

А:

```text
как сделать из Quake
современный programmable engine?
```

Добавляются:

- realtime lights/shadows;
- shaders;
- advanced particles;
- high-res textures;
- новые formats;
- расширенный QuakeC;
- собственные protocols;
- standalone games.

### FTEQW

Третья крайность.

FTEQW постепенно становится «швейцарским ножом» Quake-family technologies:

- Quake;
- QuakeWorld;
- Quake II;
- Quake III-related content;
- Hexen II;
- множество formats;
- plugins;
- QuakeC debugging;
- FTEQCC;
- split-screen;
- voice;
- большие servers.

То есть:

```text
не:
современный QuakeWorld

а:
универсальный idTech-derived runtime
```

### Ветки обмениваются кодом

GPL genealogy уже не чистое дерево.

Например:

```text
FTEQW
↓
часть technologies
↓
QSS
↓
часть technologies
↓
vkQuake
```

То есть происходит обмен «генами».

### Современные философии

**QuakeSpasm:**
> сохранить Quake и аккуратно снять ограничения.

**DarkPlaces:**
> использовать Quake как фундамент нового движка.

**FTEQW:**
> поддерживать как можно больше Quake/idTech-family технологий.

**Ironwail:**
> классический QuakeSpasm-style опыт, но с современной производительностью.

**vkQuake:**
> тот же ecosystem на современном Vulkan renderer.

Именно поэтому сегодня нет одного «правильного Quake source port». Они решают разные задачи.

## 27. Как DarkPlaces превратился из Quake source port в основу самостоятельных игр?

DarkPlaces — один из самых чистых примеров превращения:

```text
source port
↓
engine fork
↓
standalone game platform
```

### Начало

Проект начинается как экспериментальный улучшенный Quake:

- новые эффекты;
- кровь;
- decals;
- alpha blending;
- более современный OpenGL.

Но затем **DarkPlaces Engine** и **DarkPlaces Mod** становятся разными вещами.

Это главный рубеж:

```text
DarkPlaces ≠ один мод Quake

DarkPlaces Engine
   ├── Quake
   ├── DarkPlaces mod
   └── другие games
```

### Renderer

DarkPlaces постепенно получает:

- 32-bit color;
- realtime lights;
- realtime shadows;
- stencil shadows;
- GLSL;
- per-pixel lighting;
- bump mapping;
- parallax/offset mapping;
- high-res textures;
- cubemaps;
- advanced particles/decals;
- новые model formats.

В какой-то момент «GLQuake с эффектами» уже вообще не описывает реальность.

### Поддержка новых data formats

Engine начинает понимать не только Quake BSP/MDL.

Появляется поддержка разных:

- map formats;
- model formats;
- image formats;
- shader-like descriptions.

То есть renderer уже обслуживает **общую игровую платформу**, а не только Quake resources.

### QuakeC → DarkPlaces gameplay API

Это, пожалуй, ещё важнее renderer.

DarkPlaces массово расширяет QuakeC builtins:

- graphics;
- networking;
- filesystem;
- strings;
- input;
- UI;
- particles;
- models;
- entities;
- client-side systems.

Теперь QuakeC — уже не просто:

```text
язык для монстров Quake
```

а:

```text
game scripting language
для DarkPlaces engine
```

### Engine/game feedback loop

Новая игра хочет feature:

```text
game needs X
↓
engine receives X
↓
QuakeC API expands
↓
следующие games могут использовать X
```

Это нормальная зрелая relationship между game и engine.

### Infrastructure

Чтобы стать standalone engine, нужны не только graphics:

- filesystem;
- game directories;
- configs;
- master servers;
- downloads;
- network protocols;
- UI;
- input;
- game-specific defaults.

DarkPlaces всё это выращивает.

### Nexuiz

Главное доказательство.

```text
DarkPlaces
+
свои maps/models/textures
+
свой QuakeC
+
свой multiplayer
=
Nexuiz
```

Quake assets не нужны.

Игра сама начинает активно требовать новые возможности движка.

### Steel Storm

Ещё более важный жанровый тест.

Steel Storm — top-down hovercraft shooter.

```text
Quake
↓
DarkPlaces
↓
top-down commercial arcade shooter
```

То есть engine ancestry больше не диктует FPS-perspective.

Разработчики Steel Storm прямо объясняли, что выбрали DarkPlaces из-за:

- знакомства с Quake modding;
- GPL;
- отсутствия риска закрытой лицензии;
- QuakeC;
- готового art/tool pipeline.

### Другие типы игр

Исторические DarkPlaces game modes включали:

- Nexuiz;
- Prydon Gate;
- GoodVsBad2;
- OpenQuartz;
- BattleMech;
- другие проекты.

Prydon Gate вообще демонстрирует top-down point-and-click action-RPG направление.

### Главный перелом

Пока движок требует:

```text
pak0.pak
pak1.pak
```

его легко воспринимать как Quake-port.

Когда новая игра говорит:

```text
Quake assets не нужны
мне нужен только engine
```

это уже самостоятельная engine platform.

DarkPlaces дошёл именно до этого состояния.

## 28. Как связаны DarkPlaces, Nexuiz и Xonotic?

Самая короткая схема:

```text
Quake — 1996
   ↓
GPL source
   ↓
DarkPlaces
   ↓
Nexuiz Classic — 2005
   ↓
community fork — 2010
   ↓
Xonotic
```

Но есть важная ловушка: после раскола появляется **другая коммерческая игра с названием Nexuiz на CryEngine 3**.

Поэтому правильное дерево:

```text
                         QUAKE
                           │
                           ▼
                      DarkPlaces
                           │
                           ▼
                    NEXUIZ CLASSIC
                         2005
                           │
               ┌───────────┴───────────┐
               │                       │
       community/code lineage     бренд Nexuiz
               │                       │
               ▼                       ▼
            XONOTIC               Nexuiz 2012
          DarkPlaces               CryEngine 3
```

### Nexuiz

Оригинальный Nexuiz начал развиваться в начале 2000-х и вышел в 2005 году.

Это уже полноценная standalone игра на DarkPlaces:

- Windows/Linux/Mac;
- multiplayer;
- bots;
- собственные maps;
- weapons;
- QuakeC game code;
- собственные assets.

Nexuiz становится одной из главных production нагрузок DarkPlaces.

Игра начинает сама формировать engine: некоторые extensions появляются именно потому, что они нужны Nexuiz.

### Раскол 2010 года

Вокруг бренда Nexuiz заключается коммерческая сделка для создания нового проекта.

Часть community воспринимает это как отход от прежнего open-source проекта.

Разработчики/контрибьюторы форкают существующую свободную codebase.

Так появляется **Xonotic**.

### Xonotic — настоящий технологический наследник

Xonotic не просто «вдохновлён Nexuiz».

Он начинается как прямой fork и продолжает:

- DarkPlaces lineage;
- QuakeC gameplay;
- часть content/workflow;
- multiplayer infrastructure;
- community development.

Дальше проект постепенно переписывает собственные code/assets и приобретает отдельную идентичность.

### Коммерческий Nexuiz 2012 — другая технологическая ветка

Название сохраняется, engine lineage — нет.

```text
Nexuiz brand
↓
IllFonic
↓
CryEngine 3
```

Поэтому для исследования id Tech:

```text
Quake
↓
DarkPlaces
↓
Nexuiz Classic
↓
Xonotic
```

— реальная технологическая линия.

А:

```text
Nexuiz Classic
↓
Nexuiz 2012
```

— в основном линия бренда.

### Xonotic и DarkPlaces сегодня

Xonotic использует собственную интегрированную ветку DarkPlaces technology.

При этом современный upstream DarkPlaces подчёркивает, что Xonotic и DarkPlaces — уже организационно отдельные проекты.

То есть:

```text
              DarkPlaces lineage
                    │
         ┌──────────┴──────────┐
         │                     │
upstream DarkPlaces      Xonotic integration
                               │
                             Xonotic
```

### QuakeC lineage

Особенно поразительно, что gameplay-подход QuakeC живёт через всю цепочку:

```text
Quake
↓
QuakeC
↓
DarkPlaces extensions
↓
Nexuiz gameplay
↓
Xonotic gameplay
```

Язык, созданный ради Ogre/Shambler/rocket launcher в 1996 году, становится фундаментом современной самостоятельной multiplayer game.

### Главное

DarkPlaces → Nexuiz → Xonotic — это открытая community-линия Quake.

Она отлично контрастирует с корпоративной:

```text
Quake
↓
Valve
↓
GoldSrc
↓
Source
↓
Source 2
```

Один и тот же предок породил два совершенно разных вида эволюции:

- proprietary corporate lineage;
- GPL/open-source lineage.

## 29. Почему новые коммерческие игры продолжают использовать потомков Quake engine спустя почти 30 лет?

Потому что возраст движка сам по себе почти ничего не говорит о пригодности **его потомка**.

Когда современная игра использует DarkPlaces, FTEQW или другой Quake-derived engine, она не запускается на `quake.exe` 1996 года с прикрученным widescreen. Между ними лежат десятилетия переписывания renderer'а, networking, QuakeC API, файловой системы, форматов ресурсов, лимитов и платформенного кода.

Самый наглядный пример — **WRATH: Aeon of Ruin**. Полная версия вышла 27 февраля 2024 года, а издатель 3D Realms прямо рекламирует её как игру, работающую на legendary Quake 1 technology. Фактически WRATH использует собственный fork DarkPlaces.

Цепочка реально выглядит так:

```text
Quake — 1996
   ↓
source release — 1999
   ↓
DarkPlaces
   ↓
WRATH-specific fork
   ↓
WRATH: Aeon of Ruin — 2024
```

Почти 28 лет между исходным Quake и новым коммерческим релизом.

### Причина №1 — полный исходный код

С закрытым middleware разработчик обычно живёт внутри границ API владельца.

С Quake-derived open-source engine:

```text
есть проблема
↓
открываешь engine source
↓
меняешь сам движок
```

DarkPlaces — GPL engine с современным rendering, расширенным QuakeC и дополнительными map/model formats.

FTEQW — GPL engine с собственным QuakeC compiler, plugin architecture и огромной поддержкой форматов.

Для маленькой технически сильной команды это означает:

> не просить владельца движка добавить feature, а написать её самому.

### Причина №2 — нет engine royalties владельцу Quake lineage

GPL не запрещает коммерческие игры.

Нужно соблюдать условия лицензии для derivative engine code, но не существует обязательного royalty id за каждую проданную копию современного Quake-derived проекта.

Удобная модель:

```text
GPL ENGINE
   │
   ├── source доступен
   ├── vendor lock-in минимален
   └── можно fork'нуть

GAME ASSETS
   │
   └── собственный коммерческий контент
```

Именно это привлекало, например, разработчиков Steel Storm.

### Причина №3 — десятилетия production testing

Quake descendants прошли через:

- Quake;
- QuakeWorld;
- тысячи mods/maps;
- DarkPlaces;
- Nexuiz;
- Xonotic;
- Steel Storm;
- другие проекты.

Это означает огромный накопленный инженерный капитал.

```text
filesystem?
давно работает

client/server?
давно обстрелян

console/cvars?
давно понятны

QuakeC VM?
используется десятилетиями
```

FTEQW сегодня вообще поддерживает несколько idTech-family игр, множество formats, plugins, voice chat, split-screen и крупные servers.

Это уже не археологический код.

### Причина №4 — компактность и понятность

Современный general-purpose AAA engine огромен.

Небольшой Quake-derived engine зачастую реально можно понять целиком:

```text
main loop
renderer
server
client
QuakeC VM
network
collision
filesystem
```

Для специализированной indie-команды это может быть важнее, чем тысячи готовых систем Unreal, из которых 95% не нужны.

### Причина №5 — QuakeC

Quake ещё в 1996 году отделил:

```text
ENGINE
↓
QuakeC VM
↓
GAMEPLAY
```

DarkPlaces и FTEQW затем расширили эту идею.

Маленькая команда может быстро менять gameplay без необходимости переписывать core engine.

Это одна из причин удивительной долговечности архитектуры.

### Причина №6 — огромная экосистема знаний

За десятилетия появились:

- map editors;
- compilers;
- converters;
- QuakeC compilers;
- документация;
- tutorials;
- mapping practices;
- community tools.

Поэтому:

```text
старый engine
+
30 лет community knowledge
```

может быть продуктивнее:

```text
новый собственный engine
+
нулевая экосистема
```

WRATH сознательно привлекала специалистов из Quake mapping/modding scene.

### Причина №7 — для конкретного жанра ограничения старой архитектуры могут быть неважны

Если игра — компактный stylized FPS, ей не обязательно нужны:

- open-world streaming;
- MetaHuman;
- Nanite-подобная geometry virtualization;
- огромный cinematic pipeline;
- тысячи skeletal NPC.

Зато могут быть критичны:

```text
быстрый input
точное movement
предсказуемая collision
лёгкие levels
быстрая iteration
полный control
```

И здесь Quake-derived engine чувствует себя естественно.

### Причина №8 — old-school ограничения могут быть частью художественного языка

Если тебе нужен visual/level-design язык поздних 90-х:

- low-poly;
- BSP-like spaces;
- lightmap aesthetic;
- высокая скорость;
- плотная геометрия;

современный универсальный engine иногда приходится специально ломать и ограничивать.

Quake lineage уже естественно говорит на этом языке.

WRATH даже продаёт своё технологическое происхождение как часть идентичности.

### Причина №9 — низкие hardware requirements

Компактный engine + относительно простой content pipeline позволяют делать игру очень лёгкой.

WRATH — хороший пример современной коммерческой игры с удивительно низкими системными требованиями.

Старый lineage не гарантирует производительность автоматически, но избавляет от огромного количества современного framework overhead.

### Причина №10 — кроссплатформенность

За десятилетия Quake source переносили практически куда угодно.

DarkPlaces/FTEQW накопили серьёзные platform abstraction layers.

WRATH в итоге вышла не только на PC, но и на современные консоли.

То есть:

```text
Quake ancestry
≠
старый Windows-only software
```

### Причина №11 — минимальный vendor risk

С proprietary middleware владелец может менять:

- цены;
- лицензию;
- поддержку;
- доступ;
- roadmap.

С GPL fork:

```text
upstream исчез?
↓
fork остаётся
↓
поддерживаешь сам
```

WRATH буквально имеет собственную DarkPlaces-derived engine branch.

### Причина №12 — человеческий опыт

Если разработчик двадцать лет работает с Quake mapping/QuakeC/source ports, старый знакомый stack может быть продуктивнее «более современного», но незнакомого движка.

Разработчики Steel Storm прямо говорили, что пришли из Quake modding community и уже знали art pipeline, tools и технологию.

### Причина №13 — естественная лестница modder → commercial developer

Quake ecosystem позволяет расти так:

```text
играю в Quake
↓
делаю карту
↓
учу entities
↓
учу QuakeC
↓
лезу в engine
↓
делаю собственный fork
↓
делаю standalone game
```

Не нужно однажды выбрасывать весь накопленный опыт и переходить в совершенно другой стек.

### Почему тогда все не используют Quake?

Потому что свобода оплачивается engineering time.

Если нужны:

- advanced animation;
- cinematic tooling;
- modern PBR authoring;
- navmesh;
- open-world streaming;
- visual scripting;
- production-grade editor;
- console certification tooling;

Quake-derived engine часто скажет:

> строй сам.

То есть экономическая формула:

### Unreal-подобная модель

```text
огромный готовый engine
+
огромный tooling stack
+
меньше собственного low-level engineering
```

### Quake-derived модель

```text
маленький понятный engine
+
полный source
+
свобода
+
нет vendor lock-in
-
много систем придётся строить самому
```

Поэтому Quake особенно подходит командам, у которых:

```text
ENGINE PROGRAMMING SKILL
>
BUDGET / CONTENT SCALE
```

### WRATH как итог всей истории

```text
1996
Quake
   ↓
1999
GPL source
   ↓
DarkPlaces
   ↓
WRATH-specific fork
   ↓
2024
новая коммерческая игра
```

Это не потому, что за 28 лет индустрия не придумала ничего лучше.

А потому что:

```text
DarkPlaces ≠ Quake 1996
```

при том что:

```text
DarkPlaces ← Quake 1996
```

Это похоже на Unix lineage: современная система может происходить от технологии десятилетней давности, не являясь той же самой реализацией.

### Итог для базы

Новые коммерческие проекты продолжают обращаться к потомкам Quake из-за комбинации:

```text
полный source
+
GPL
+
отсутствие engine royalties
+
маленькая понятная архитектура
+
QuakeC
+
30 лет tools/community knowledge
+
полный контроль
+
кроссплатформенность
+
низкие hardware requirements
+
возможность бесконечно fork'ать
```

В обмен разработчик принимает:

```text
старую архитектурную ДНК
+
меньше современных готовых systems
+
необходимость самому быть engine developer
```

Quake-derived engine сегодня — нишевый инструмент.

Но для правильной команды и правильной игры эта ниша может быть идеальной.

**WRATH: Aeon of Ruin (2024)** — один из лучших современных контраргументов фразе:

> «движку почти 30 лет, значит он давно бесполезен».
